# BEP 19: External Agent Runtimes — Claude Code and Codex

- **Status:** **Partially implemented** — §6 Layers 1–3 shipped, Layer 4's **Codex** runtime built and Layer 5's `codex` and `claude-code` extras packaged; the Codex runtime validated live against a real ChatGPT subscription (three runs on 2026-09-25, §8.1); Layer 4's Claude Code runtime in progress — the vendor behaviour its confinement rests on is pinned in CI and §3.5.3 has been corrected from it; `ClaudeCodeAgent` constructs (config, the permission mapping, no repository settings by default, the fail-closed preflights) and runs a turn that resumes the chat's session, validates structured output, streams it as `TurnEvent`s and persists itself, not yet interruptible, time-bounded or confined — and its live validation not started. See §8.1 for readiness per track and §9 for what changed.
- **Depends on:** BEP 18 (the embedding SDK — this BEP widens two of its promised signatures and adds one method to `BosApp`), BEP 13 (concentric rings — `AgentPort` lands in the innermost ring, the two runtimes in `bos.extensions`), BEP 4 (micro-kernel — `ep_tool` is the registry the MCP egress reads), BEP 6 (configuration architecture), BEP 12 (`AgentResult` and structured output — both runtimes must produce one), BEP 5 (`ChatStore` — what BOS persists for an external chat)
- **Blocked by:** nothing. Every dependency exists in the repo today.

## 1. Motivation

BOS can drive any model LiteLLM can reach, and it cannot drive either of the two agent harnesses people actually use for code: Claude Code and Codex. Those are not models. Each is a complete agent loop with its own tools, its own context management, its own permission system, and — the part that matters commercially — its own subscription login. Pointing `model = "claude-opus-4-5"` at LiteLLM gets the model and throws away the harness, and pays per token for what a subscription already covers.

Both vendors now ship an official Python SDK that exposes the whole harness as a library:

- **`claude-agent-sdk`** 0.2.159 (`anthropics/claude-agent-sdk-python`). Ships platform wheels that bundle the Claude Code CLI — `manylinux_2_17_x86_64` is 97 MB. Requires `mcp>=1.23,<3`, `anyio`, `jsonschema`, `sniffio`.
- **`openai-codex`** 0.156.1 (`openai/codex`, `sdk/python`). Pure-Python wheel plus a pinned `openai-codex-cli-bin==0.156.1` that carries the `codex` binary. Speaks JSON-RPC to `codex app-server` over stdio.

The adaptation turns out to be close to total. Every load-bearing parameter of `Agent.run` has a counterpart on both sides — session resume, per-turn model, reasoning effort, JSON-schema structured output, interrupt, an event stream, working directory, a system-prompt slot. §3.9 is the full table, including the seven things that have no counterpart and are dropped on purpose.

### 1.1 What this BEP is *not* claiming

- **Not that the two runtimes are equivalent.** They are not, and §3.5 is an entire section about the one place the gap is dangerous: directory confinement. Codex enforces it with an OS sandbox; Claude Code has one for bash commands only, so BOS builds the file-tool confinement itself, out of a `PreToolUse` hook.
- **Not that subscription auth is guaranteed.** BOS requires that the native runtime's existing login be used and fails loudly when it cannot confirm that. Whether a given account or SDK version permits a given use is between the operator and the vendor. BOS stores no subscription token.
- **Not that both runtimes have been validated against a real subscription.** The Codex runtime has — three runs against the owner's ChatGPT login on 2026-09-25, recorded criterion by criterion in §8.1; run 2 recorded a security defect, and run 3, after the fix, confirmed it closed (§3.5.4). Claude Code has not been run against one at all. §7 separates the criteria a fake can satisfy from the ones that need a real login.
- **Not a background-task system.** `ask()` blocks for the duration of the native turn, exactly as it does for a BOS agent. §2.2 says why, and §1.2 what the alternative would have cost.

### 1.2 Runtimes are agents, not delegation tools

The obvious alternative is to expose each runtime as a set of tools — start a task, continue it, poll it, cancel it — so a cheap BOS main agent delegates to Claude or Codex and collects the result later. That is a task-orchestration subsystem: a task record store, a session-mapping table, an owner check, a concurrency limiter, a completion-notification path back into the parent turn, and a recovery story for tasks found in an unknown state after a restart.

Making the runtimes *agents* removes all of it, because BOS already has every one of those mechanisms for agents:

- Delegation: `_HarnessAgentRunner.run()` ([`harness.py:282-314`](../../src/bos/core/harness.py)) calls `create_agent(kind)`. The existing `AskSubagent(role=…)` tool therefore reaches an external runtime the day the runtime is an agent kind, with no new tool and no change to [`plugins/subagent.py`](../../src/bos/plugins/subagent.py).
- Turn lifecycle, interrupt, event fan-out, parent/child nesting: `AgentActor` and the gateway, unchanged.
- Persistence and recovery: `ChatStore`, unchanged.

The cost is that a delegated turn is synchronous. §2.2 accepts that.

## 2. Goals and Non-Goals

### 2.1 Goals

1. `create_agent("claude-code")` and `create_agent("codex")` return objects that satisfy every contract `AgentActor`, `_HarnessAgentRunner` and `boscli ask` already require of an agent, backed by the vendors' official Python SDKs.
2. Adapt as much of `Agent.run`'s parameter surface as each SDK supports, and enumerate — in this document and in an error or log line at runtime — every parameter that is dropped.
3. Make the per-agent options an embedder needs available at construction time and in config: permission level, working directory, native model, system prompt, timeout, MCP tool exposure — and let a project give a runtime any number of named instances with their own prompts.
4. Confine an external runtime to a declared directory, and state per runtime what that confinement is actually made of.
5. Expose a chosen subset of `ep_tool` tools to both runtimes through **one** MCP server with one implementation and one authorization check.
6. Give a host application a read path for an external chat's messages without hijacking `ChatStore`.
7. Add no new scheduler, queue, task store, event bus, or config layer.

### 2.2 Non-Goals

1. **Asynchronous / background external tasks.** `ask()` returns when the native turn ends. A host that wants to survive a disconnect already has the gateway's turn machinery. Revisit only with a concrete use case the gateway cannot serve.
2. **Approval round-trips to a human.** BOS has no channel that carries an approval request to a user and back. Every permission decision in this BEP is made by policy, synchronously, without blocking — see §3.5.4. Building that channel is its own BEP.
3. **Mirroring native transcripts into `ChatStore`.** §3.7.
4. **Cross-runtime session migration.** Switching an established chat from `codex` to `claude-code` starts a new native session. BOS says so rather than claiming a lossless move.
5. **ACP.** Not a dependency, not implemented. A future ACP runtime would implement the same `AgentPort` and reuse §3.4–§3.8 unchanged.
6. **Remote Codex Cloud.** Local runtime only.
7. **Reimplementing either harness's tool loop, context compaction, or subagents.**

## 3. Design

### 3.1 Runtime shape

| Thing | What it is at runtime | Where it lives | Lifecycle |
|---|---|---|---|
| `AgentPort` | A `Protocol` — no runtime object | `bos/core/agent/contract.py` | n/a |
| `ClaudeCodeAgent` | A plain object, one per `create_agent` call | `bos/extensions/runtimes/claude_code.py` | Built by `create_agent`, appended to `AgentHarness._owned`, closed by `_aclose` on harness exit |
| `CodexAgent` | Same | `bos/extensions/runtimes/codex.py` | Same |
| The `claude` CLI subprocess | One per turn, spawned by `ClaudeSDKClient.connect()` | Child of the BOS process | Created in `run()`, disconnected in the same `finally` |
| The `codex app-server` subprocess | **One per `CodexAgent`**, spawned lazily on the first call that needs the client | Child of the BOS process | Created by the first `run()` — or the first `native_messages()` (§3.7), which goes through the same `_ensure_client` — and killed by `CodexAgent.aclose()` |
| `BosToolMcpServer` | An in-process `uvicorn.Server` on `127.0.0.1:<ephemeral>` serving one Starlette app | `bos/extensions/runtimes/mcp_egress.py` | One per harness, started lazily the first time an external agent declares at least one `mcp_tools` name the host has an `ep_tool` for (§3.8) — a list that is empty, or wholly unmatched, starts none; closed by `_aclose` last, after every runtime |

Nothing here is a daemon, a queue, or a scheduled job. The only long-lived additions to a BOS process are the `codex app-server` child and the loopback MCP server, and both exist only when an external agent was built.

### 3.2 The seam: two reserved agent kinds, and agents that inherit from them

`AgentHarness.create_agent` ([`harness.py:411-489`](../../src/bos/core/harness.py)) ends in `agent: Agent = _apply(Agent, kwargs); return agent` and has no substitution point. This BEP adds one:

```python
# Kind -> "module:Class", not the class itself: this module is imported on a
# base install with no extras, so importing a vendor SDK here would break
# `import bos.sdk`. Resolved by importlib on first build, per kind.
EXTERNAL_AGENT_KINDS: dict[str, str] = {
    "claude-code": "bos.extensions.runtimes.claude_code:ClaudeCodeAgent",
    "codex": "bos.extensions.runtimes.codex:CodexAgent",
}
```

The values are dotted paths, not the classes themselves — `harness.py` is on the import path of a base `bos-ai` install with neither extra present, and importing `claude_agent_sdk` or `openai_codex` at module load would make `import bos.sdk` itself require both 97 MB vendor wheels. `_load_external_runtime(runtime)` ([`harness.py:72-91`](../../src/bos/core/harness.py)) resolves one entry with `importlib.import_module` on first build and reports the real `ImportError` plus the extra to install if it fails (§7.10) — it does not assume the failure means the extra is missing, since the same exception shape also covers a genuinely broken import inside an installed runtime module.

An agent is backed by one of them when **either** its kind is a reserved name, **or** its resolved spec carries `external_runtime` — which is what inheriting from a reserved name produces (§3.4). The branch goes immediately after `merged_cfg` is computed and **before** `_bind_plugins_for_agent`, because none of plugins, the local `ToolRegistry`, `ResolvedToolSet`, `_CompositePluginInterceptor` or `_PluginPromptProvider` applies to a runtime that owns its own tool loop:

```python
merged_cfg = _deep_merge(copy.deepcopy(agent_defaults), agent_cfg or {})
runtime = kind if kind in EXTERNAL_AGENT_KINDS else merged_cfg.get("external_runtime")
if runtime is not None:
    external = _load_external_runtime(runtime)(
        kind=kind or runtime, cfg=merged_cfg, chat_store=self.chat_store, workspace=self._workspace,
        structured_validator=_default_structured_validator(),   # the same one every Agent gets — BEP 12, §3.9
        mcp=self._ensure_tool_mcp_server,   # §3.8; an accessor, not a server — calling it is
                                            # what starts the loopback server, and a runtime
                                            # with nothing servable never calls it
    )
    self._owned.append(external)        # _aclose() on harness exit — §3.1
    return external
```

`.get`, not `.pop`: `external_runtime` **stays in `merged_cfg`**, which becomes the runtime's own `cfg`. Not because anything downstream reads it there — nothing in the repo does; `CodexAgent` takes its runtime as a constructor literal and `resolved_config` restates that, and stripping the key from the cfg leaves the suite green. The reason is simply that there is nothing to gain by mutating: `.pop` would need a justification and has none, while leaving the key costs nothing and keeps the merged config an accurate record of what was asked for — which is what a third-party `ExternalRuntime` that echoes its raw cfg would report.

`kind` stays the agent's own name, so a Codex-backed agent called `george` reports itself as `george` through `AgentPort.name`, in events, and in `boscli inspect` — the runtime is how it is built, not who it is.

There is no extension point and no adapter abstraction. Two names, two classes, one dict. A third runtime is a third entry; if a fourth ever needs to come from outside the repo, *that* is when an extension point earns its keep.

**`ep_agent` is not the seam.** It is a factory for agent *config dicts*, not agent objects — [`extensions/agents/bos_config.py:174-195`](../../src/bos/extensions/agents/bos_config.py) returns `{"description": …, "system_prompt": …, "tools": …, "plugins": …}`, which `bootstrap_platform` folds into `AgentRegistry`. It cannot return a runtime.

#### 3.2.1 Externally-backed agents do not inherit `[agent.defaults]`

`bootstrap_platform` merges `[agent.defaults]` under every registered agent ([`workspace.py:683-685`](../../src/bos/config/workspace.py)). A project with `[agent.defaults] model = "gpt-4o"` would silently hand `"gpt-4o"` to Codex as a *native* model name, along with `max_tokens`, `plugins` and the rest.

The registration loop therefore starts from `{}` instead of `agent_defaults` when the name is reserved **or** the inheritance-resolved spec carries `external_runtime` — the second half is what keeps `george` covered, since `george` is not a reserved name. `config_specs` is already inheritance-resolved at that point in the loop, so the check is available where it is needed. Each runtime then validates its own config strictly (§3.4).

### 3.3 `AgentPort` — widening four signatures

`Agent` is a concrete class, and four signatures name it:

| Site | Today |
|---|---|
| [`harness.py:411`](../../src/bos/core/harness.py) | `create_agent(...) -> Agent` |
| [`sdk/_app.py:123`](../../src/bos/sdk/_app.py) | `BosApp.agent(kind) -> Agent` |
| [`sdk/_app.py:140`](../../src/bos/sdk/_app.py) | `BosApp.build_agent(kind) -> Agent` |
| [`gateway/actors/agent_actor.py:105`](../../src/bos/gateway/actors/agent_actor.py) | `AgentActor(agent: Agent, ...)` |

A repo-wide scan of what those consumers actually *call* returns four members, and no more:

| Member | Call sites |
|---|---|
| `ask(chat_id, content, interrupt=, ctx_metadata=, llm_args=, event_sink=, turn_id=, commit_observer=)` | [`agent_actor.py:358`](../../src/bos/gateway/actors/agent_actor.py) |
| `run(chat_id, content, *, …, schema=, max_schema_retries=)` | [`harness.py:307`](../../src/bos/core/harness.py), [`cli/commands/agent.py:442`](../../src/bos/cli/commands/agent.py) |
| `request_stop()` | [`agent_actor.py:133`](../../src/bos/gateway/actors/agent_actor.py) |
| `name` | [`agent_actor.py:540`](../../src/bos/gateway/actors/agent_actor.py), via `getattr` |

So `bos/core/agent/contract.py` gains exactly that, and the four signatures widen to it:

```python
@runtime_checkable
class AgentPort(Protocol):
    """What a host requires of an agent, whichever runtime backs it (BEP 19 §3.3)."""

    @property
    def name(self) -> str: ...
    def request_stop(self) -> None: ...
    async def ask(self, chat_id: str, content: MessageContent, ...) -> str: ...
    async def run(self, chat_id: str, content: MessageContent, *, ..., schema: dict[str, Any] | None = None,
                  max_schema_retries: int = 1) -> AgentResult: ...
```

`Agent` satisfies it structurally and is not modified.

**The rejected alternative** was `class CodexAgent(Agent)` overriding only `run()`, which would have left all four signatures untouched and changed no contract. It was rejected because it is inheritance used to borrow an interface: it makes `isinstance(codex_agent, Agent)` true for an object that runs none of `Agent`'s behaviour, forces the two runtimes to satisfy `Agent.__init__`'s required `llm` and `consolidator` kwargs ([`agent.py:264-286`](../../src/bos/core/agent/agent.py)) with objects they never call, and inherits ~700 lines of turn loop, compaction and structured-output retry as dead weight with nothing marking it inapplicable. `AgentPort` is also a written-down list of what a host may rely on, which is the thing to consult when a later BEP adds an SDK-level method.

`AgentPort` is what a *host* requires of any agent. The harness requires more of a vendor-backed one, so `contract.py` also gains **`ExternalRuntime`** — `AgentPort` plus `aclose()`, a `resolved_config` property, and the six-keyword `__init__` that `create_agent` builds every runtime through. Both names are exported from `bos.core.__all__`. It is separate from `AgentPort`, not folded into it, because BOS's own `Agent` has neither member and needs neither: it has nothing to close, and its config is not something `inspect` reads back. `aclose` has to be *in a protocol* rather than a convention because `AgentHarness.__aexit__` drains `_owned` through a `hasattr` probe — a runtime that forgets it is skipped in silence and leaks its child process, and the protocol is what makes a type checker catch that. `resolved_config` is a `Mapping` and not the parsing layer's dataclass because this ring may not import from `bos.extensions` (BEP 13). Fallout: none beyond this BEP — it is a new name, nothing existing is asked to satisfy it, and it is `AgentPort`, not this, that the four widened signatures use (§5.1).

#### 3.3.1 `boscli inspect` must stop assuming `Agent`

[`cli/commands/inspect.py:204,219-223`](../../src/bos/cli/commands/inspect.py) reaches past the public surface into `agent._prompt_provider._plugins`, `agent._kind`, `agent._name`, `agent._model` and `agent._tools`. Against an external runtime those raise `AttributeError`. `_agent_capabilities` gains a branch: for an object that is not an `Agent`, report `kind`, `name`, the resolved runtime, the resolved `cwd`, the `permission` level, the resolved `mcp_tools`, and the subset of those the host has no `ep_tool` for, with `plugins` and `skills` empty. All of it from the runtime's `resolved_config`, which `ExternalRuntime` promises, so nothing here is a duck-typed reach and nothing requires the agent to have run a turn — which matters for the unavailable names, since the MCP server that would otherwise notice them is built lazily on the first turn and `inspect` runs none. This is the operator's inspection path (§4.3) and is the only place in the repo that reads an agent's internals.

### 3.4 Configuration

The same keys work from TOML and from `agent_cfg`; `AgentConfig` is `extra="allow"` ([`schema.py:62`](../../src/bos/config/schema.py)) so they pass through `_agent_config_to_core_kwargs` untouched. Each runtime validates them itself and **raises on an unknown key** — the pass-through is a transport, not a licence.

```toml
[agents.codex]
cwd = "services/api"            # workspace-relative; see §3.5.1
permission = "workspace-write"  # REQUIRED, no default; see §3.5
model = "gpt-5.1-codex"         # native model name, passed through verbatim
system_prompt = "..."           # → developer_instructions
timeout_seconds = 1200
auth = "subscription"           # default; see §3.10.3
mcp_tools = ["DeskCreateTask"]  # default []; see §3.8

[agents.codex.native_options]   # escape hatch; everything but the reserved set (below)
personality = "concise"
```

```toml
[agents.claude-code]
cwd = "."
permission = "read-only"
model = "claude-opus-4-5"
setting_sources = []            # Claude only; the default. "project" is opt-in — see §3.5.3
mcp_tools = []
```

`[agents.claude-code]` is a legal TOML table: bare keys permit `-`.

**`native_options` is the escape hatch, and it is trusted config.** Its entries are handed to the runtime's own session-start call as keywords — for Codex, `thread_start`/`thread_resume`, so `personality = "concise"` above becomes `thread_start(personality="concise")`. One entry is treated differently and says so: a `config` sub-table is *merged into* the `config=` override rather than passed as a keyword, because Codex's own `config.toml` keys are not keywords — that is the route §3.4.1.4's `project_doc_max_bytes` takes.

The runtime declares which settings it sets for itself, and `parse_external_config` **rejects** a `native_options` naming any of them, at construction, with the key in the message. For Codex that set is `sandbox`, `approval_mode`, `cwd`, `model`, `developer_instructions` and `base_instructions` — the whole of what `_thread_for` sends as typed parameters — plus two sub-tables of `config`, which is merged rather than owned: `config.mcp_servers`, where BOS writes its egress, and `config.sandbox_workspace_write`, which BOS does not send at all but which reaches the sandbox `permission` chose. A reserved sub-table is refused in either spelling — as a nested table, or as one of Codex's own dotted override paths (`sandbox_workspace_write.writable_roots`) — because to Codex those are the same setting. Rejected rather than last-write-wins or warned past, because `sandbox` and `approval_mode` are derived from `permission` and `cwd` is the containment boundary: a config that could quietly replace any of them would undo §3.5 while looking like a tuning knob. An escape hatch is for the settings BOS does not touch, and the parse error is what keeps that true.

**What the reserved set does and does not buy.** It stops `native_options` *renaming* a decision BOS sends: for the settings BOS passes as typed parameters, measurement confirms the parameter wins over anything the `config` layer says — checked for `sandbox_mode`, `approval_policy`, `cwd` and `model`. That is every typed parameter that decides what the runtime may *do*; the two prompt keys are not in the measured set because a prompt decides no permission. What it cannot do is make the `config` table safe in general, because Codex lets a decision be reached under a second name: `sandbox_mode` in `config` loses to BOS's `sandbox`, but `sandbox_workspace_write.writable_roots` is not a typed parameter at all, and under `permission = "workspace-write"` the server honours it. That table is therefore reserved too — every sub-key of it, in either spelling, since a dotted key inside `config` reaches the same setting as a nested one. **The list is a denylist arrived at by probing, not an enumeration** — there is no listing of Codex's config surface that BOS can read, so it is not provably complete, and §8.2 carries what that leaves open. Read `native_options` as config trusted at the same level as `permission`, written by the same person, and not as something the runtime bounds.

A name the runtime's call does not have is *not* caught here — BOS does not carry a copy of the vendor's signature — so it surfaces as a `TypeError` from the vendor on the first turn, naming the key — and suggesting the intended one when it is a near miss (`personalty` → "Did you mean 'personality'?"; an unrecognisable name gets no suggestion). That is the intended trade: an escape hatch that silently dropped what it did not recognise would be worse than one that fails loudly. A *table* BOS reserves inside (`config`) is checked, though, because a non-table there would fail inside BOS's own merge and name nothing.

**For Claude Code the reservation is an allowlist, enumerated from the vendor's own type.** Its entries become fields of the `ClaudeAgentOptions` each client is built from, and `ClaudeAgentOptions` is a dataclass, so — unlike Codex's config surface, which is untyped and could only be probed — every setting the SDK accepts can be listed. `ClaudeCodeAgent` sorts each field into exactly one of three sets: **BOS-owned**, which BOS sets or has reserved to set (among them `permission_mode`, `sandbox`, `settings`, `setting_sources`, `strict_mcp_config`, `hooks`, `can_use_tool`, `tools`, `env`, `resume`, and `extra_args`, which carries `--replay-user-messages` (§3.9) and would carry any flag a host put there); **refused**, neither set by BOS nor safe to forward (among them `cli_path`, `add_dirs`, `plugins`, `agents`, and `user` — which is not a session label: the SDK hands it to `anyio.open_process(user=…)`, so it is the OS user the CLI runs as); and **allowed**, forwarded verbatim (`fallback_model`, `max_budget_usd`, `betas`, `thinking`, `max_thinking_tokens`, `task_budget`). A `native_options` naming anything outside the allowed set — including a name that is no field at all, so a typo fails at `create_agent` here rather than at the first turn — is refused at construction with each key and the reason its class gives. The enumeration's source is the vendor's type: `test_native_options_classification_partitions_the_vendor_fields` asserts that the three sets partition `dataclasses.fields(ClaudeAgentOptions)`, so an SDK release that adds a field fails CI until someone classifies it. That is what the Codex list cannot be — a denylist that is complete only as far as probing reached (§8.2) — and why this one is closed.

**`_parent = "codex"` and `_parent = "claude-code"` work, and are the main way to configure one.** An agent that inherits from a reserved kind is a *named instance* of that runtime: it gets its own name, its own prompt, its own `cwd` and permission, and it is addressable everywhere a BOS agent is — `[runtime.actors.*]`, `AskSubagent(role=…)`, `boscli ask --agent`, `app.agent()`.

```markdown
<!-- <bos_dir>/agents/george.md -->
---
_parent: codex
cwd: services/api
permission: workspace-write
mcp_tools:
  - DeskCreateTask
---
You are George, the implementer for the payments service. …
```

`george` now has Codex's capabilities under its own name and its own prompt, and a sibling `martha.md` differs only in its body. The bare kinds stay available — `[agents.codex]` gives the workspace one default profile, and `create_agent("codex")` works with no config at all — but nothing forces a project to address the runtime by the vendor's name.

The mechanism is the existing resolver plus one table. `_resolve_agent_inheritance(specs, factory_specs)` already accepts any parent present in `specs` or `factory_specs` and deep-merges the parent's resolved spec underneath the child ([`workspace.py:439-483`](../../src/bos/config/workspace.py)), so the two reserved kinds are supplied as pseudo-factory specs at that one call site:

```python
_EXTERNAL_RUNTIME_SPECS = {"codex": {"external_runtime": "codex"},
                           "claude-code": {"external_runtime": "claude-code"}}
config_specs = _resolve_agent_inheritance(config_specs, factory_specs | _EXTERNAL_RUNTIME_SPECS)
```

Three consequences fall out of the resolver's existing behaviour rather than needing new code. `george` inherits `external_runtime`, which is what §3.2 dispatches on. If the project also writes `[agents.codex]`, `parent in specs` is true and its resolved spec merges in too, so shared `cwd` / `permission` / `model` can be set once and each named instance overrides only what differs. And chains (`harry` → `george` → `codex`) resolve transitively with cycle detection, unchanged.

The merge is **only** at that call site: the reserved kinds are deliberately *not* added to the `{**factory_specs, **config_specs}` enumeration that registers agents, so a project that never mentions them gets no phantom `codex` agent in `AgentRegistry.describe()` and no new ambiguity in `resolve_default_agent()`.

`external_runtime` is written by the resolver, never by hand. A user-authored `external_runtime` key is rejected by the strict validation in §3.4, with a message naming `_parent` — one way to say it.

Profiles can equally come from the actor table, which needed no change either:

```toml
[runtime.actors.coder]
agent = "george"                       # or "codex" for the bare default profile
agent_cfg = { permission = "read-only" }
```

`BosApp.build_agent` gains an additive optional parameter so the programmatic path can set these without TOML:

```python
coder = await app.build_agent("codex", agent_cfg={"cwd": "services/api", "permission": "workspace-write",
                                                  "mcp_tools": ["DeskCreateTask"]})
```

This is also the API for choosing which tools reach MCP (§3.8) — one key, one source of truth, rather than a second `expose_tools()` entry point that could disagree with the config.

#### 3.4.1 System prompt: `system_prompt` and `base_instructions`

`system_prompt` keeps its name and means **"the instructions for this agent"** on an external runtime too — but it is **layered on top of** the runtime's own prompt rather than replacing it. Replacing is a separate key, `base_instructions`, and it is rarely what anyone wants.

Each runtime has three prompt layers. BOS owns exactly one of them:

| Layer | Owner | Claude Code | Codex |
|---|---|---|---|
| The harness's own base prompt | The vendor | Claude Code's system prompt | codex base instructions |
| **The agent's instructions** | **BOS — `system_prompt`** | `--append-system-prompt` | `developer_instructions` |
| Project docs under `cwd` | The repo | `CLAUDE.md` — under the default `setting_sources = []`, the root file only, read by BOS and appended after `system_prompt`; loaded by the CLI itself only if a host opts into `"project"` (§3.4.1.4, §3.5.3) | `AGENTS.md`, read by codex; no knob observed to suppress it (§3.4.1.4) |

- **`system_prompt: str`** → Claude Code `system_prompt={"type": "preset", "preset": "claude_code", "append": …}`; Codex `thread_start(developer_instructions=…)`. The harness keeps its own tool guidance.
- **`base_instructions: str`** → Claude Code the plain-`str` form of `system_prompt`; Codex `thread_start(base_instructions=…)`. You now own the prompt and the harness's tool guidance is gone. Setting both keys is an error.

Appending is the default because the destructive reading is the dangerous one: Claude Code's system prompt is what makes Claude Code's tools work, and a config author writing `system_prompt = "You are the implementer."` is expressing a role, not asking for the harness to be lobotomised. An earlier draft of this BEP renamed the key to `instructions` and rejected `system_prompt` outright; that is reverted, because it would also have broken the file route below — where the key is not written by hand at all.

#### 3.4.1.1 How a host supplies it

Two routes, both existing mechanisms, and **no path-valued config key**. A `*_file` key would have to resolve relative to something, and in a host holding several workspaces (§3.12) that "something" is exactly the ambiguity to avoid. Files are read by the layer that already knows the workspace root; everything below it sees a resolved string.

**1. A file, per named agent — the authoring route.** `resolve_agents()` scans `[platform.agent_dirs]` (default `./agents`, resolved against that workspace's `bos_dir`) for `.toml` and `.md`. In a `.md` file the YAML frontmatter is the agent config and **the body is `system_prompt`**; the agent's name is the filename stem ([`workspace.py:529-564`, `:184-204`, `:974-982`](../../src/bos/config/workspace.py)). Combined with `_parent` (§3.4), one file is one named instance of a runtime — `agents/george.md`, `agents/martha.md` — and the prompt is just the body, where a prompt belongs.

This needs **no change to the loader**: the body lands in `system_prompt`, which is the key §3.4.1 defines. It is also why that key could not be renamed or rejected — nobody writes it by hand on this route.

One frontmatter constraint, which the existing parser imposes rather than this BEP: `_parse_simple_yaml_mapping` is a small subset of YAML, so keys must be plain scalars or simple indented blocks ([`workspace.py:229-262`](../../src/bos/config/workspace.py)). The list form shown in §3.4 for `mcp_tools` is within it; anything more structured belongs in a `.toml` agent file or in `[agents.*]`.

**2. `agent_cfg`, programmatically — the embedding route.** A host that keeps prompts in its own store (per tenant, in a database, templated per request) passes the resolved string, to a kind the workspace's own config does not already build:

```python
coder = await app.build_agent("codex", agent_cfg={"permission": "read-only", "system_prompt": prompts.for_tenant(t)})
```

`agent_cfg` is the override layer for that call, so it wins over `[agents.codex]` if written. It is **not**, however, a way to reconfigure an agent that `BosApp` already built: `__aenter__` pre-builds and caches every kind your config names in `[agents]` — including a named instance such as `george` from `agents/george.md` — before application code runs, and `build_agent` caches per kind. So `build_agent("george", agent_cfg={…})` finds `george` already cached and raises, naming the cache and what to do instead, rather than silently discarding the override ([`sdk/_app.py`](../../src/bos/sdk/_app.py)'s `BosApp.build_agent`). Reach for `agent_cfg` on a kind the config leaves unbuilt — a bare reserved kind with no `[agents.<reserved>]` table, as above, or a new name whose `agent_cfg` carries a `_parent` — or call `harness.create_agent` directly, which has no per-kind cache.

A `_parent` in `agent_cfg` names a reserved runtime or any registered agent, and resolves to what the same settings under `[agents.<name>]` with that `_parent` would: a registered agent's `AgentRegistry` defaults already hold its whole resolved chain, so they are deep-merged under `agent_cfg`, with the child's own name as its `kind` — per-agent plugin state such as memory is keyed by `agent_name or kind`, and the parent's `agent_name` is not inherited, on this route as in config (BEP 6's `_parent` addendum; this route also drops one from `[agent.defaults]`, which it cannot tell apart), so each child gets a store of its own unless it names one — and a reserved runtime is seeded with the marker `_EXTERNAL_RUNTIME_SPECS` writes, its own `[agents.<runtime>]` config included when there is one. The settings are given in `agent_cfg`'s own shape, which is the harness's argument shape rather than TOML's (`tools` is a list, not a `[tools]` table). So `build_agent("martha", agent_cfg={"_parent": "codex", "permission": "read-only"})` is a second Codex instance, and `build_agent("george-b", agent_cfg={"_parent": "george", "cwd": "services/b"})` is `george` in another directory. `create_agent` refuses, rather than drops, a `_parent` that is neither; one given to a kind that is already registered, whose defaults fold in a lineage of their own; and one whose runtime contradicts the kind or an `external_runtime` in the same `agent_cfg` ([`harness.py`](../../src/bos/core/harness.py)'s `_resolve_agent_cfg_parent`). An actor's `agent_cfg` is the exception: an actor selects a declared agent with `agent`, so `_parent` there is refused when the config loads, naming the actor. The TOML equivalent for a per-actor profile is a section — which, unlike an inline table, can hold a multi-line string:

```toml
[runtime.actors.coder.agent_cfg]
permission = "workspace-write"
system_prompt = """
You are the implementer for this service. …
"""
```

Precedence, lowest to highest, within one `create_agent` call: the reserved kind's `{"external_runtime": …}` → `[agents.<reserved>]` if written → the named agent's own spec (`.md` frontmatter and body, or `[agents.george]`) → `[runtime.actors.*].agent_cfg` → the `agent_cfg` passed to `build_agent` / `create_agent`. This is BEP 6 merge order with the §3.4 parent link slotted in; nothing new. Through `BosApp.build_agent`, this order is reachable only on a kind's first build — a kind already cached cannot re-enter it (above).

#### 3.4.1.2 What belongs in it

The append slot should carry **only what the harness cannot already know**. Everything else is duplication, and duplication of a vendor's own prompt makes the agent worse, not better.

Worth writing: the agent's role in this deployment and who consumes its reply (`AskSubagent` and host code are not a human at a terminal); the output contract — what "done" and "blocked" look like; the boundary, in words, matching §3.5's `permission` and `cwd`, including that it should report rather than widen its own scope; and the host's domain vocabulary when §3.8 exposes domain tools, since `DeskCreateTask` means nothing without it.

Not worth writing: how to use `Read` / `Edit` / `Bash`, how to search a repo, how to write good code, or general helpfulness. The harness's own prompt does all of that better.

#### 3.4.1.3 The Claude Code default is a trap

`ClaudeAgentOptions.system_prompt` defaults to `None`, and `SubprocessCLITransport._build_command` turns `None` into `--system-prompt ""` — an *empty* prompt, not Claude Code's own ([`subprocess_cli.py:572-573`](https://github.com/anthropics/claude-agent-sdk-python)). The way to get the CLI's default is `{"type": "preset", "preset": "claude_code"}` with no `append`, which matches none of the branches and so emits **no flag at all** (`:577-585`).

So `ClaudeCodeAgent` always sets the option explicitly: the preset with `append` when there is something to append — `system_prompt`, the root `CLAUDE.md` BOS reads (§3.4.1.4), or both — the bare preset when there is neither, and a plain `str` for `base_instructions`. Leaving the SDK default in place would ship an agent with Claude Code's tools and none of the prompt that drives them — a quality regression with no error anywhere to point at. §7.13 therefore asserts the emitted CLI flags, not the resolved config. Codex is inert by comparison: omitting both instruction keys leaves its defaults alone.

#### 3.4.1.4 Project docs

The third layer is authored by the repo, not by BOS, and the two runtimes take it in differently.

**Claude Code: BOS reads the root `CLAUDE.md` and appends it.** The CLI loads `CLAUDE.md` itself only when `setting_sources` contains `"project"` (the SDK's own docstring; `test_a_host_that_opts_into_repo_settings_runs_the_repos_commands` observes it), and the default is `[]`, because `"project"` also loads the repo's `.claude/settings.json`, whose hooks and helper commands run on the host outside the sandbox (§3.5.3). So unless `"project"` is set, BOS reads `<cwd>/CLAUDE.md` as text and appends it to the agent's instructions: the repository's instructions reach the model, and nothing the repository configures runs. The owner chose this over stating that the file is not loaded. The rules:

- **One file, as text.** Only `<cwd>/CLAUDE.md`. This is not Claude Code's memory loading, which walks from `cwd` up through its ancestors loading `CLAUDE.md`, `.claude/CLAUDE.md` and `.claude/rules/` in each directory, expands `@` imports, and adds `CLAUDE.local.md` and the user's own file under their own sources (read from the CLI 2.1.281 source). BOS reads none of those: an `@` import stays literal text, and no `.claude/CLAUDE.md`, no `CLAUDE.md` in an ancestor or a subdirectory, no rules file, no `CLAUDE.local.md` and no user-level file is read — `test_only_the_root_claude_md_is_read` pins the import, `CLAUDE.local.md` and a subdirectory. A host that wants the CLI's own loading opts into `"project"`, at the cost §3.5.3 names.
- **Contained, and this rule is security-critical.** BOS reads the file in its own process, outside every confinement, and sends what it read to the model provider, so a repository whose `CLAUDE.md` is a symlink to `~/.ssh/id_rsa` must not get BOS to read the key and ship it. The path is resolved, symlinks included, before anything is read, and must be a regular file inside `cwd`, which `parse_external_config` has already resolved. A symlink that stays inside `cwd` is followed; one that leaves it, a dangling one, a directory or a FIFO is not read, and BOS logs a WARNING that names the path (`test_a_claude_md_that_is_not_a_regular_file_inside_the_root_is_not_read`). The open follows no final symlink and does not block, so a FIFO swapped in after the check cannot hang the turn, and what was opened is checked again: `fstat` must report a regular file, and on Linux (`/proc/self/fd`) and macOS (`F_GETPATH`) the kernel's own answer for where the open file is must lie inside `cwd`. That closes the window in which a process in the same directory swaps a path component for a symlink between the check and the open (`test_the_file_actually_opened_is_checked_again`). Each layer is pinned on its own: the first check refuses before anything is opened, and `test_a_claude_md_swapped_after_the_check_is_still_not_read` swaps in a FIFO, a directory and a symlink out of `cwd` after it, with the kernel's answer withheld. On other platforms only the first check and the open's own guards run, and the macOS call is taken from its documentation, not measured on a macOS host. Against the real CLI, a `CLAUDE.md` symlinked to a canary file outside `cwd` put the canary in no request the model received (`test_a_claude_md_symlinked_outside_the_root_never_reaches_the_model`). The rule is about names, not files: a hard link inside `cwd` to a file outside it is a regular file inside `cwd` by every path the kernel reports, and it passes. That is accepted, not overlooked. Git has no representation for a hard link, so no checkout delivers one, and whatever can make one can read the target without BOS: a process running as BOS's user, or an agent able to write in its root, which at `workspace-write` can already read outside it through bash (fact 6b) and at `full-access` is not confined at all.
- **At most 40,000 bytes.** That is where Claude Code itself calls a memory file large: it warns once one passes about 5% of the context window, with a floor of 40,000 characters, and skips one only past 4 MiB (read from the CLI 2.1.281 source). BOS pays for the file in the system prompt of every turn, so it truncates there rather than warn and send it all: past the cap it appends the first 40,000 bytes, then the line `[BOS truncated this CLAUDE.md at 40000 bytes.]`, and logs a WARNING that names the file. Counted in bytes, the cap never admits more than 40,000 characters. The bytes are decoded as UTF-8 with invalid sequences replaced (U+FFFD) rather than refused, which also covers a character the cap cuts in two.
- **After `system_prompt`, in the system prompt.** The file goes into the preset's `append`, after the agent's own `system_prompt` and a blank line, under the heading `# CLAUDE.md in the working directory`; with no `system_prompt` it is the whole `append` (`test_the_root_claude_md_is_appended_after_the_agents_own_instructions`). Never with `base_instructions`: that key means the host owns the whole prompt, and BOS does not even read the file (`test_the_root_claude_md_never_joins_base_instructions`, `test_the_root_claude_md_is_not_even_read_when_it_could_not_be_used`). Nor under `"project"`, where the CLI loads it itself and BOS does not send a second copy (`test_the_root_claude_md_is_left_to_the_cli_when_project_settings_load`); `"local"` without `"project"` gets both, `CLAUDE.local.md` from the CLI and `CLAUDE.md` from BOS. BOS's copy does not land where the CLI's would: measured against the real CLI with the fake model, the append reaches the request's `system`, while a memory file the CLI loads travels in `messages` — the same text, carried as standing instructions instead of as context. `test_by_default_nothing_the_repo_authors_runs_or_reaches_the_model` and its control pin where each file landed.
- **Read at every turn.** Each turn starts its own CLI (§3.10.1), which reads memory afresh when it starts, so BOS reads the file again for every turn (`test_the_root_claude_md_is_read_again_for_every_turn`): an agent that edits it changes what its next turn sees, as under the CLI's own loading. Writes to it are not denied. It is a file in the agent's root like any other, and whatever the agent leaves there meets the same rules at the next read. Each WARNING — a file refused, or cut short — is logged once per agent for each path and reason, not at every turn, so a misconfigured file does not log a line per turn forever (`test_each_claude_md_warning_is_logged_once_per_agent`).
- **Off with the CLI's own switches.** BOS's read stands in for the CLI's memory loading, so it obeys every switch the CLI's memory gate obeys (`aH()` in the CLI 2.1.281 source): `CLAUDE_CODE_DISABLE_CLAUDE_MDS`, safe mode (`CLAUDE_CODE_SAFE_MODE`), and bare mode (`CLAUDE_CODE_SIMPLE`, which the gate honours only when no directory is added — and `add_dirs` is refused, §3.4). With any of them set, BOS does not read the file. It applies the CLI's own rule for each — set only when, lower-cased and trimmed as JavaScript's `trim()` trims, it is `1`, `true`, `yes` or `on` (`Oe`, read from source) — so `0`, `false` or an empty value leave the read on (`test_the_clis_switches_for_memory_files_turn_off_bos_read_too`). The `--bare` and `--safe-mode` flags are the same switches, and BOS never passes them, since `extra_args` is refused. Bare mode is refused under the subscription login (§3.10.3), so it matters under `api_key`. `CLAUDE_CODE_DISABLE_CLAUDE_MDS` is also the opt-out for a host that wants no repository text in the prompt: an existing CLI switch, not a new BOS key. BOS reads it from its own environment, which the CLI inherits (§3.12), at every turn; it does not see a value set only in a settings file's `env`.

**Codex.** `AGENTS.md` is read by codex itself, and **this BEP offers no way to suppress it for Codex.** `project_doc_max_bytes` and `project_doc_fallback_filenames` are config keys in the 0.156.1 binary, and either can be sent through `native_options.config`. Live validation sent `project_doc_max_bytes = 0` that way in runs 2 and 3: `thread_start` accepted it and the turn completed, but the reply still reflected the `AGENTS.md` placed in `cwd` both times. So what is proven is the plumbing — a config key reaches the child and is accepted — and not that this key, or any other, suppresses the file. Why it had no effect was not measured, and no other knob is offered in its place. `project_doc_fallback_filenames` was not exercised.

### 3.5 Permission and directory confinement

This is the section to read before trusting anything else in this BEP. The two runtimes enforce confinement with different machinery at different strengths, and the config key is deliberately a BOS-owned three-value enum so the asymmetry is described once, here, instead of being implied by two vendors' mode names.

**`permission` bounds the agent, not the host — and on the filesystem, not the tools.** Two separate limits on how far this section's guarantee reaches, and both matter.

The first: `permission` is what BOS tells the runtime, and the runtime enforces it against the *agent*. It is not a limit on the person who wrote the config. That person can widen their own agent's sandbox through `native_options`, deliberately, because Codex accepts sub-settings of the chosen sandbox mode that are not the setting BOS sends — `sandbox_workspace_write.writable_roots` under `permission = "workspace-write"` is the measured case, and the whole table is reserved for that reason, in either spelling (§3.4), but the reserved list is a denylist and not a proof (§8.2). So: a `workspace-write` agent is confined to its workspace *by this enum*, and `native_options` is config trusted alongside it.

The second: within what it does bound, `permission` says what the runtime may do to the disk, and nothing else. A `read-only` agent still has an unrestricted callable path into every `ep_tool` its `mcp_tools` lists, mutating ones included, because the MCP egress is gated by that list and by a bearer token (§3.8) and not by this enum — and because BOS pre-approves its own MCP server: on Codex under the `never` approval policy every permission uses (§3.5.4), on Claude Code in what `can_use_tool` answers (§3.5.3). Before the Codex pre-approval existed this sentence was false as built: live validation's `read-only` agent had its call refused with "MCP tool call requires approval, but approval policy is never", which was the first sign the approval policy was not what §3.5.4 said. That is deliberate — the host chose those tools, and a tool that writes to the host's own database has nothing to do with whether the agent may write to `cwd` — but it is the opposite of what "read-only" suggests, so: the two gates are independent, and `mcp_tools` is the one that decides what the agent can *change* through BOS.

For Codex, `permission` chooses a sandbox, and the sandbox is the whole boundary (§3.5.2, §3.5.4):

| `permission` | Codex |
|---|---|
| `read-only` | `Sandbox.read_only` + `ApprovalMode.deny_all` |
| `workspace-write` | `Sandbox.workspace_write` + `ApprovalMode.deny_all` |
| `full-access` | `Sandbox.full_access` + `ApprovalMode.deny_all` |

For Claude Code, BOS assembles it from five parts; §3.5.3 has the measurements behind each, and what is not yet measured. The confinement is **deny-by-default over the CLI's own offered tool list**, not an enumeration of "mutating tools": a `tools=` allowlist per level (an excluded tool is never offered and is not callable — measured, even against a trusted repo's `permissions.allow`), and the hook as the per-call gate on top of it.

| `permission` | `permission_mode` | `tools=` (offered) | `PreToolUse` hook | bash sandbox | `can_use_tool` |
|---|---|---|---|---|---|
| `read-only` | `default` | `Read` only | denies any tool outside the allowlist, and any file-tool path outside the root or inside `<CLAUDE_CONFIG_DIR>` | off (Bash not offered) | answers what `permission` already decided, never awaits: BOS's own MCP tools and any allowlisted, hook-vetted call yes, anything else no |
| `workspace-write` | `acceptEdits` | `Read`, `Write`, `Edit`, `NotebookEdit`, `Bash` | denies any tool outside the allowlist, and any file-tool path outside the root, inside `<CLAUDE_CONFIG_DIR>`, or (under a `setting_sources` opt-in) inside `<cwd>/.claude` | `{"enabled": True, "allowUnsandboxedCommands": False, "failIfUnavailable": True}` | as above, and Bash yes — the sandbox confines it |
| `full-access` | `bypassPermissions` | every tool except the cross-session pair (`ListAgents`, `SendMessage`) and the interactive trio (`AskUserQuestion`, `EnterPlanMode`, `ExitPlanMode`) | denies only those excluded tools should one ever reach it; confines nothing on the filesystem | off | never called (`bypassPermissions` approves first) |

The cross-session pair and the interactive trio are excluded at **every** level, `full-access` included: they reach other Claude Code sessions on the machine, or ask a user / toggle plan mode, none of which any `permission` grants and BOS has no channel for (§2.2.2). MultiEdit, Glob and Grep — named by an earlier version of this row — are not offered by CLI 2.1.281 and are gone from it.

**`workspace-write` can write `/tmp`, by Codex's default, and BOS documents that rather than overriding it.** The resolved policy has `excludeSlashTmp: false` and `excludeTmpdirEnvVar: false`. Observed in live runs 2 and 3: a `workspace-write` agent wrote a file under `/tmp` outside its `cwd`. `$TMPDIR` was unset in both runs, so a write there was not observed; the policy says it is writable too. A host that needs `/tmp` excluded has no BOS-level setting for it — `config.sandbox_workspace_write` is reserved (§3.4). Claude Code differs here: a bash `touch` directly under `/tmp` fails inside its sandbox and does not reach the host's `/tmp` (§3.5.5).

For Codex the approval mode is the same in every row, and that is the point: `deny_all` asks no one, so `permission` decides only the sandbox and the sandbox is the whole boundary. This table said `ApprovalMode.auto_review` for the bottom two rows until live validation showed that `auto_review` hands escalations to an LLM reviewer inside Codex rather than to BOS (§3.5.4).

The §3.5.4 approval handler is installed on the Codex client at **every** level, not only `workspace-write`: it is the answer to a request to escalate past whichever sandbox the row above set, and there is no level at which BOS can grant one.

**For Claude Code, `permission_mode` belongs to BOS, not to config.** It is derived from `permission`, and a `native_options` naming it is refused (§3.4). Three of the SDK's six modes — `typing.get_args(PermissionMode)` lists them — are deliberately never used. `plan` is not a write guard: under it an out-of-root `Write` reached `can_use_tool` and, allowed, wrote (fact 5; the facts are §3.5.3's, numbered as its tests are). `dontAsk` refuses, without asking anyone, a `Write` that nothing has pre-approved — fact 2 pins that for an out-of-root one; that it refuses an in-root one too was measured while §3.5.3 was written and is not pinned — so under it `workspace-write` could not write at all. And `auto` has the CLI ask a classifier model before a tool runs: an LLM deciding whether the call goes ahead, the Claude Code analogue of the Codex `auto_review` above, which §3.5.4 records as the defect live validation found. Against the fake model the classifier returns no verdict and the CLI blocks the call (fact 2); what it decides with a real model was not measured, and does not need to be, because a model is not what should decide what `permission` already has.

**This column said otherwise until measurement showed it could not hold, before any of it was built.** It mapped `read-only` to `plan` with a `can_use_tool` that denied every write tool, and `workspace-write` to `acceptEdits` with a `can_use_tool` path check. `plan` is not a write guard (fact 5), so `read-only` rested on `can_use_tool` alone. And `can_use_tool` is not asked about a call something else has already approved: in a workspace the operator has trusted, the repo's own `.claude/settings.json` allow rules approved an out-of-root `Write` with the callback never called (fact 4), so the path check would not have run for exactly the write it existed to stop. It is the same kind of finding as the Codex reviewer above, made against the real CLI with a fake model rather than by live validation; §3.5.3 has the measurements and §9 the record.

#### 3.5.1 `cwd`

Resolved relative to the harness workspace (`AgentHarness._workspace`), then `Path.resolve()`d and required to be inside it. A `cwd` that escapes fails at `create_agent`, not at first turn. The resolved absolute path is the confinement root for §3.5.2 and §3.5.3, and is what `boscli inspect` reports.

#### 3.5.2 Codex: OS sandbox

`Sandbox.read_only` / `workspace_write` / `full_access` map to `SandboxMode.read_only` / `workspace_write` / `danger_full_access` at thread start and to `ReadOnlySandboxPolicy` / `WorkspaceWriteSandboxPolicy` / `DangerFullAccessSandboxPolicy` at turn start ([`openai_codex/_sandbox.py`](https://github.com/openai/codex)). The codex runtime enforces these at the OS level. `workspace_write` confines writes to the thread's `cwd` plus configured writable roots — and, by default, `/tmp` and `$TMPDIR` (§3.5). Neither policy restricts reads (§3.5.5). **This is real confinement** of writes, and it is the one BOS does not have to build.

#### 3.5.3 Claude Code: a `PreToolUse` hook for file tools, the CLI's OS sandbox for bash

Three things about the SDK's options must be said plainly, all read from `claude_agent_sdk/types.py` 0.2.159:

1. `ClaudeAgentOptions.cwd` sets the subprocess working directory. It does not restrict anything.
2. `add_dirs` *widens* access beyond `cwd`. There is no narrowing counterpart.
3. `SandboxSettings` covers **bash commands only**, is `enabled: False` by default, and is documented as macOS/Linux only. Its own docstring is explicit: *"Filesystem and network restrictions are configured via permission rules, not via these sandbox settings — Filesystem read restrictions: Use Read deny rules; Filesystem write restrictions: Use Edit allow/deny rules."*

`permission_mode` is an approval policy, not a sandbox, and `can_use_tool` is not one either. Which of them decides a given call cannot be read off their names, so this design rests on what the real CLI was measured to do. Each fact below is a test in `tests/test_claude_code_vendor_facts.py` that drives the `claude` CLI bundled in `claude-agent-sdk` 0.2.159 (CLI 2.1.281) through `ClaudeSDKClient` against a scripted fake Messages API — the model is fake; the CLI, the SDK and every permission decision are the vendor's — and is cited here by the number that file gives it:

| Fact | Test | What it pins |
|---|---|---|
| 2 | `test_fact_2_a_pretooluse_hook_sees_every_call_and_its_deny_holds_in_every_mode` | A `PreToolUse` hook fires once per tool call, and its deny stops an out-of-root `Write`, in each of the six modes; the model is told the hook's reason. Which calls reach the callback therefore depends on the mode, on the command, and — where a host has opted into the repository's settings — on permission rules the repository itself controls. So BOS confines with the two mechanisms that depend on none of that — **tool-argument path denial plus a bash OS sandbox** — and gives `can_use_tool` the one job it can do:

- **Tools the model is offered — a `tools=` allowlist per level.** `tools=` is the CLI-level allowlist BOS sends; a tool not on it is never offered and is **not callable even when the model asks** ("No such tool available … disabled for this session", pinned), and not re-addable through a trusted repo's `permissions.allow` either (measured while building the hook, not pinned). It is deny-by-default over the CLI's own offered list (see the enumeration below): `Read` at every level; `Write`/`Edit`/`NotebookEdit`/`Bash` at `workspace-write` and `full-access`; nothing else below `full-access`; and never the cross-session pair or the interactive trio. This is the first layer, and it is why "read-only writes nothing" holds without the hook ever seeing a `Write` — the CLI rejects it first.
- **File tools — a `PreToolUse` hook.** An async callback on `HookMatcher(matcher=None)`, which matches every tool; fact 2 measured it firing once per call in all six modes. It is the per-call gate on top of `tools=`: it denies any tool outside the level's allowlist (a backstop for the day `tools=` does not hold, e.g. a subagent, and what denies the cross-session/interactive tools should one ever reach it), and for a tool that takes a path it resolves the argument — relative to `cwd`, then through `Path.resolve()`, so `..`, symlinks and `~` cannot escape — and denies the call when the result leaves the root, with a reason the model sees; for anything else it returns no decision. Under `full-access` it checks only the allowlist and confines nothing on the filesystem. At `read-only` and `workspace-write` it denies writes into the CLI's own config directory (`CLAUDE_CONFIG_DIR`, `~/.claude` by default) as well, whatever else it decides: the CLI carves its auto-memory directory there out of the permission check, and a `read-only` agent's `Write` into `<CLAUDE_CONFIG_DIR>/projects/<slug>/memory/` landed with no permission prompt, where writes elsewhere outside `cwd` were refused for want of one (§3.12; §8.2(g)) — now closed twice over: `Write` is not offered at `read-only`, and where it is offered (a `cwd` that contains the config directory, e.g. `$HOME`) the hook denies the path. When a host opts into the repo's settings (`setting_sources` includes `"project"` or `"local"`), the hook also denies the agent's own writes under `<cwd>/.claude/`, so an agent cannot plant settings for its own next turn. Its deny held in all six modes, `bypassPermissions` included (fact 2), and against a trusted repo's allow rule (fact 4) — exactly where `can_use_tool` is not asked. It never blocks or awaits anything slow: it runs inside the CLI's tool path. It passes BOS's own MCP tools (`mcp__…`, §3.8) and the CLI's synthetic `StructuredOutput` tool through with no decision. §7.18 asserts its deny on every file tool, per level, against the real CLI (`tests/test_claude_code_confinement.py`).

  *What it must cover is enumerated from what the CLI offers the model, not from memory, and that enumeration is now the code's `_TOOL_LEVELS` and pinned by `test_the_offered_tools_are_all_classified`.* CLI 2.1.281 offers twenty tools with no permission handler, and three more when one is present (`can_use_tool`, which BOS sets at `read-only` and `workspace-write`): the interactive `AskUserQuestion`, `EnterPlanMode` and `ExitPlanMode`. The full set is: `Agent`, `AskUserQuestion`, `Bash`, `CronCreate`, `CronDelete`, `CronList`, `Edit`, `EnterPlanMode`, `EnterWorktree`, `ExitPlanMode`, `ExitWorktree`, `ListAgents`, `NotebookEdit`, `Read`, `ReportFindings`, `ScheduleWakeup`, `SendMessage`, `Skill`, `TaskStop`, `WebFetch`, `WebSearch`, `Workflow`, `Write`. An MCP server adds its own (`mcp__…`), which the hook passes through. `MultiEdit`, `Glob` and `Grep`, which the previous version of this section named, are not offered by CLI 2.1.281 and are gone. The path-taking tools BOS offers below `full-access` are `file_path` (`Read`, `Write`, `Edit`) and `notebook_path` (`NotebookEdit`); `EnterWorktree` (`path`) and `Workflow` (`scriptPath`) also take a path but are offered only at `full-access`, where the hook path-checks nothing, so the file-tool path map needs only the first four. Each tool's classification (`_TOOL_LEVELS`), taken from the descriptions the CLI gives the model: `Read`/`Write`/`Edit`/`NotebookEdit` are the file tools (path-checked); `Bash` is the OS-sandbox tool; `ListAgents`/`SendMessage` reach "other local Claude sessions on this machine" and `AskUserQuestion`/`EnterPlanMode`/`ExitPlanMode` need an interactive user or the plan-mode UX, so all five are excluded at **every** level; `EnterWorktree`/`ExitWorktree` (create a worktree and switch the session into it), `CronCreate`/`CronDelete`/`CronList` (a durable `CronCreate` persists to `.claude/scheduled_tasks.json`), `Workflow` (persists its script under the session directory), `Agent` (launches subagents; whether the hook sees a subagent's own tool calls is not measured, §8.2, but need not be — `Agent` is excluded below `full-access` regardless, so no confined agent spawns one), `ScheduleWakeup`, `TaskStop`, `WebFetch`/`WebSearch` (network egress; policy open, below), `Skill` and `ReportFindings` are excluded below `full-access` (deny-by-default, not measured safe under a permission bound). A CLI that adds a tool fails `test_the_offered_tools_are_all_classified` until someone classifies it (§8.2).

- **Bash — the CLI's OS sandbox, required, and set to refuse rather than degrade.** Under `workspace-write`, `sandbox={"enabled": True, "allowUnsandboxedCommands": False, "failIfUnavailable": True}`; under `read-only` `Bash` is not offered (`tools=`); under `full-access` the sandbox is off. Parsing shell commands for paths is not attempted. With its dependencies present, the sandbox confines bash **writes**: an out-of-root `touch` fails with "Read-only file system" under `acceptEdits` and `bypassPermissions` alike, and a `touch` under `/tmp` does not reach the host's `/tmp` (fact 6b). It does not confine bash **reads**: a `cat` of a file outside `cwd` returned it (fact 6b). `can_use_tool` was asked about none of those commands — under `acceptEdits`, the SDK's documented `autoAllowBashIfSandboxed` default approves them — so it is the sandbox, not the permission layer, that blocks. Measured while the hook was built: a `bwrap` that is installed but exits non-zero (so BOS's construction check, which only looks it up on `PATH`, passes) does **not** run the command unsandboxed — the command fails closed ("Exit code 1 / bwrap: broken"), not an escape (R13); §8.2 keeps the separate question of a `bwrap` that starts but cannot create a namespace.

  Left to itself, the sandbox **fails open**: with a dependency missing, `enabled` plus `allowUnsandboxedCommands: False` warns "Sandbox disabled" on stderr and runs the command unsandboxed (fact 6). `failIfUnavailable` turns that into a refusal: the CLI exits with "Sandbox required but unavailable" before any model call, and nothing runs (fact 6c). The key is not in the SDK's `SandboxSettings` TypedDict, but the SDK copies the `sandbox` dict into `--settings` unchanged (`subprocess_cli.py:519`), and CLI 2.1.281 honours it. `allowUnsandboxedCommands: False` is what stops a command asking to leave the sandbox: the Bash tool still offers the model a `dangerouslyDisableSandbox` parameter with the sandbox on, and the SDK's docstring says that with `False` every command must run sandboxed or be in `excludedCommands` — read from source, not measured.

  So the refusal has layers, and the CLI's is the authority. At `create_agent`, `workspace-write` is refused on Windows, for which the SDK does not document the sandbox, and wherever the sandbox's dependencies are missing, with a message naming what to install: on Linux, `bwrap` and `socat` on `PATH` — the two things the CLI's own dependency check (`M_` in the CLI 2.1.281 source) needs the host to provide. The check also needs ripgrep, which the CLI supplies itself unless a settings file names `sandbox.ripgrep`, and it refuses WSL 1 as an unsupported platform; BOS's check leaves both to it (read from source; fact 6 pins that a missing `socat` is named). The CLI takes `sandbox.bwrapPath` and `sandbox.socatPath` from settings in place of `PATH`, so a repository's settings could point it at a fake bwrap — which the default below, loading no repository settings file, puts out of a repository's reach. Managed settings, which always load, could still set them: that is the administrator's policy (§8.2). On macOS the CLI's check tests nothing; BOS looks for `/usr/bin/sandbox-exec`, through which the CLI runs every sandboxed command (read from source; not measured — no macOS host was available). That check is the early, friendly error, and it can only defer a failure to the CLI, never permit one: wherever the CLI's own check finds the sandbox unavailable, `failIfUnavailable` refuses the first turn, whatever BOS's check concluded. Behind both, BOS watches the CLI's stderr under `workspace-write` for the "Sandbox disabled" warning through a per-turn `stderr` callback (`_sandbox_tripwire`), and if it appears it interrupts the turn (Task 7's machinery) and raises `_SandboxDisabledError` — a cheap third layer for any degrade path the key does not cover, pinned by `test_the_sandbox_tripwire_ends_the_turn`. A `bwrap` installed but broken (exits non-zero) does not degrade to unsandboxed: the command fails closed (R13, above). Whether a `bwrap` that starts but cannot create a namespace is caught is still not measured (§8.2).

- **Each CLI's settings are its own.** The SDK sends `sandbox` inside inline `--settings` JSON, and the CLI's bash sandbox guards a path named after it against writes: `/tmp/claude-<uid>/claude-settings-<16 hex>.json`, the hex the start of the sha256 of the settings **re-serialized as compact JSON** (read from the CLI source; `tests/test_claude_code_runtime.py`'s `_settings_mount_point` derives the name and finds the file there). The file at that path is an **empty bwrap mount point**, not the settings. A CLI that finds the path missing has bwrap mount `/dev/null` on it, which leaves the empty file on the host, and removes that file once its own sandboxed commands are done; a CLI that finds it present binds the file that is there and leaves it alone (read from source). Measured, and pinned by `test_each_clients_cli_binds_a_settings_file_of_its_own`: the file exists, empty, while a sandboxed command runs, and is gone once the turn is over. So CLIs started with byte-identical settings share one file, and a sandboxed command fails with `bwrap: Can't find source path …` when another CLI removes the file in the **narrow window** between this CLI finding it and its bwrap starting. The failure is per command and intermittent — a later command, finding the path missing, re-creates it, and two turns ordered so that one ends before the other's next sandboxed command both run fine — but under concurrency it is real: without a nonce, fact 6b failed 5 and 7 times in two samples of 24 under 4-way parallel runs, and 4 of 128 sandboxed commands failed across four runs of four concurrent CLIs; with one, none did. BOS starts one CLI per turn, and every `workspace-write` agent would send the same `sandbox` dict. BOS therefore adds a per-client nonce to the settings it sends — `{"env": {<name>: <uuid4 hex>}}` — which makes each CLI's settings, and so its file, its own. `test_each_clients_cli_binds_a_settings_file_of_its_own` pins that two clients name two files and that the real CLI holds the one its own settings name; the race itself cannot be reproduced on demand, because no ordering of turns arranges the window. **The nonce covers only the one mount point BOS can name.** To keep a sandboxed command from creating settings files, the CLI also mounts empty directories and files where protected paths are missing — under `<cwd>/.claude/`, and in ancestors inside the sandbox-writable temp root — and an empty `.claude` directory appears in the workspace on the host while a sandboxed command runs (measured, not pinned). Agents that share a `cwd` share those paths, and the same race follows: with six CLIs in one `cwd`, 3 of 180 sandboxed commands failed across five rounds, bwrap unable to bind `.claude/launch.json` (measured, not pinned). No BOS-side nonce reaches paths the repository names, and **the race is documented and accepted, not fixed.** It is rare and fail-closed: the command errors and the model is told. Two agents writing one directory at once already race on the files themselves, so a host should avoid that setup regardless and give each concurrent `workspace-write` agent its own `cwd`. And a per-`cwd` lock around sandboxed turns was deliberately not added, because it would change BOS's concurrency semantics: turns that run side by side today would queue. The test suite meets the race too when its temporary directories sit under `/tmp/claude-<uid>`: the nonce test failed in 6 of 36 runs at six-way concurrency there, and in none of 36 under pytest's default location. This paragraph first said the file held the settings, was named for the raw string, and that a failure lasted the rest of a turn; measurement corrected all three.

- **`can_use_tool` — the answer to a prompt, never the gate.** The CLI asks it only where it would otherwise prompt a user — the SDK routes the CLI's permission prompts to it (`types.py`'s `_configure_can_use_tool`) — and the hook and the sandbox, both of which run **before** it, answer first. It is kept as policy, not confinement: it answers what `permission` already decided, at once and without awaiting anyone (§3.5.4). Because the hook fires on every call and denies anything outside the allowlist or the root before the CLI asks, anything reaching `can_use_tool` is already hook-vetted, so it allows BOS's own MCP tools (`mcp__…`, §3.8) and any tool in the level's allowlist (a file tool whose path the hook confined to `cwd`, or sandboxed `Bash`), and denies anything else as a defensive backstop. Under `full-access` it is `None`: `bypassPermissions` never consults it (facts 2 and 6b; the SDK's own advisory, `types.py`'s `_get_can_use_tool_shadowed_warning`), so BOS installs no callback the SDK would warn is shadowed. **Which calls reach it, measured with BOS's mapped modes (`test_which_calls_reach_can_use_tool`): none of the in-root file or bash operations do** — `read-only` serves `Read` and offers no `Write`/`Bash`; `workspace-write` auto-allows in-root edits (`acceptEdits`) and every bash command (the sandbox is on, `autoAllowBashIfSandboxed`), so not even the `python3 -c` case that reaches it *without* a sandbox (fact 3) reaches it here; `full-access` never asks. So in practice the only calls it would answer are BOS's own MCP tools (§3.8, Task 10). Nothing in the confinement depends on its answer — the hook confines file tools, the sandbox confines bash, and a trusted repo's allow rule can approve a call before it is asked (fact 4). **The web tools (`WebSearch`, `WebFetch`) reach both the hook and `can_use_tool`** (measured, Task 8), so BOS could gate them at either; their policy is an open question (§8.2(a)), so under deny-by-default they are excluded below `full-access` until it is decided.

- **Settings files are off by default, because a settings file is code.** Left at `None`, `setting_sources` sends no `--setting-sources` at all (fact 9), and then, per the SDK's docstring, `~/.claude/settings.json`, `.claude/settings.json` and `.claude/settings.local.json` all load. BOS always sends it, and by default as `[]`, the SDK's own "isolation mode": no user, project or local settings file loads. That is not no settings at all. The CLI always loads managed settings — the machine administrator's policy under `/etc/claude-code`, and an organization's remote-managed settings — and BOS's own flag settings, and managed settings outrank BOS's `--settings`: they can override the sandbox BOS sends and carry an `apiKeyHelper` (read from source). That policy sits legitimately above BOS, and BOS does not try to overrule it (§8.2). A settings file does more than carry permission rules. Measured against CLI 2.1.281 with a hostile repository and BOS's own options: under `"project"`, the repository's command hooks (`SessionStart`, `PreToolUse`) and its `apiKeyHelper` ran on the host at every permission level, `read-only` included, and under `workspace-write` they wrote outside `cwd` while the model's own sandboxed Bash could not. None of them is a tool call, so neither `permission` nor the hook nor the sandbox reaches them. `"local"` (`.claude/settings.local.json`) behaves the same, with `CLAUDE.local.md` in place of `CLAUDE.md`, and the repository's settings `env` took effect too (measured, not pinned). Those are the measured entries of a longer list of settings that run commands, and what a settings file can do is the CLI's to extend; a denylist of such settings would be the incomplete enumeration this design has already paid for (§3.4, §3.5.4), so BOS loads none unless a host opts in. The same default closes the fake-bwrap path above. And `strict_mcp_config` is always sent, so the CLI loads only the MCP servers BOS passes: a repository's `.mcp.json` server did not start with it (pinned by the control below) and started under `"project"` without it (measured, not pinned). Under the default, none of the hostile repository's hooks, `apiKeyHelper` or `.mcp.json` server ran, and the CLI loaded neither of its memory files; its root `CLAUDE.md` reached the model all the same, in the system prompt, because BOS reads that one file as text and appends it (§3.4.1.4), and its `CLAUDE.local.md` did not reach the model at all — `test_by_default_nothing_the_repo_authors_runs_or_reaches_the_model` pins that at each level, and `test_a_host_that_opts_into_repo_settings_runs_the_repos_commands` is its control, for `"project"` at every level and for `"local"`. So the default costs the CLI's loading of the repository's memory files — imports, ancestors, `.claude/CLAUDE.md`, rules files, `CLAUDE.local.md` — but not the repository's root instructions. The operator's auto-memory is not a repository file and is not a settings source: it loads under `[]` unless switched off, and BOS switches it off (§3.12).

  `setting_sources` stays a key a host may set. Including `"project"` or `"local"` logs one WARNING at construction naming the consequence: what the repository's settings configure takes effect, and the commands they name run on the host outside the sandbox and outside `permission`. The hook must then also deny the agent's own writes under `.claude/`: the `Write` tool reached `can_use_tool` for `.claude/settings.json` and created it when allowed (measured, not pinned; the sandbox refused the same write from Bash), so without that deny an agent could plant settings for its own next turn. Under an opt-in, what the repository's settings can do to the sandbox settings BOS sends — `enabled`, `excludedCommands`, `bwrapPath` — is not measured (§8.2). `"user"` is the operator's own file rather than the repository's, and is opt-in for the reason it always was: a server whose behaviour changes with the operator's personal machine config is not reproducible.

  Under an opt-in, trust decides whether the repository's **permission rules** apply, and fact 4 measures the cost: in a workspace the CLI considers trusted, those rules approve a call before `can_use_tool` is asked — an out-of-root `Write`, in fact 4. In an untrusted workspace the CLI ignores them and says so on stderr (fact 4). Trust is read from `<CLAUDE_CONFIG_DIR>/.claude.json` when `CLAUDE_CONFIG_DIR` is set — a marker in `<HOME>/.claude.json` is then ignored (fact 4) — and from `<HOME>/.claude.json` otherwise (measured while planning, not pinned; the CLI source agrees); it is also inherited from ancestor directories up to the enclosing git root, or to `/` outside a repository (read from source, not measured). Trust decides nothing else that was measured: hooks, `apiKeyHelper` and settings `env` took effect in a workspace nobody had trusted. An inherited `CLAUDE_CODE_SANDBOXED`, which the CLI source reads as "trusted", changed nothing measured either (measured, not pinned): the permission-rule gate reads the trust recorded in the CLI's config, which that variable does not reach, so BOS sends no override (§3.12). What trust decides does not reach what the hook and the sandbox bound: the hook's deny held against the trusted repo's allow rule (fact 4), and the sandbox held under `bypassPermissions`, which approves every call (fact 6b). That is why the confinement is built from those two and not from the permission layer.

The BEP's language for this everywhere else is **"tool-argument path denial plus a bash OS sandbox"**, never "sandboxed".

**This section used to say otherwise, and measurement found it before implementation.** The first version confined file tools with `can_use_tool` — for `Read`/`Write`/`Edit`/`Glob`/`Grep`/`NotebookEdit`, resolve the path argument and deny when it leaves the root; under `read-only`, deny every mutating tool — and mapped `read-only` to `plan`. It would have been defeated twice over. `can_use_tool` is asked only where the CLI would otherwise prompt, and in a workspace the operator had trusted, the repo's own allow rules approved an out-of-root `Write` with the callback never asked (fact 4): the path check would not have run for exactly the write it existed to stop. And `plan` is not a write guard (fact 5): under it the same `Write` reached `can_use_tool` and, allowed, wrote, so `read-only` rested on that same callback. The same measurements showed the bash sandbox failing open (fact 6), which the first version guarded against only on Windows. This is the kind of finding §3.5.4 records for Codex's approvals reviewer — a design resting on an unmeasured assumption about which component decides a call — made against the real CLI with a fake model before any of the design was built, rather than by live validation after it.

#### 3.5.4 Approvals are decided by policy, never awaited

BOS has no channel that carries an approval request to a user and back (§2.2.2), so every callback BOS gives a runtime returns immediately.

For Claude Code that holds by construction for both of them: the `PreToolUse` hook and `can_use_tool` each return a decision at once (§3.5.3), and `permission_mode` is never `auto`, which would put a classifier model in front of each tool call instead (§3.5).

For Codex there is a hazard that must be handled rather than documented away: `CodexClient._default_approval_handler` **auto-accepts** — it returns `{"decision": "accept"}` for both `item/commandExecution/requestApproval` and `item/fileChange/requestApproval`. `AsyncCodex.__init__` takes only a `CodexConfig` and passes no handler down through `AsyncCodexClient` to `CodexClient`, so any escalation request that reaches it is granted silently. Left alone, `permission = "workspace-write"` would mean "anything that asks is allowed", contradicting its own config key. That handler is replaced below — but replacing it only matters for requests that *reach* it, and which requests reach it is decided by the approval policy, which is the part the first version got wrong (see the end of this section).

`CodexAgent` therefore installs its own handler on the constructed client, in `_ensure_client` and **before** the auth preflight — the first call that can spawn the child, and so the first moment a server request can arrive:

```python
# BEP 19 §3.5.4. The SDK's default handler auto-accepts every escalation and
# AsyncCodex exposes no way to replace it, so we reach the sync client that owns
# the transport. test_codex_approval_handler_attribute_exists fails loudly if a
# future openai-codex renames this, rather than silently restoring auto-accept.
client._client._sync._approval_handler = self._deny_approval
```

There is no `permission` argument and no per-level branch: `_deny_approval` refuses every approval request at every level. The sandbox is the real boundary and is already set per turn from `permission`; an approval request only ever arrives to escalate *past* it, and with no channel to a human, "no" is the only answer BOS can honestly give — under `full-access` too, where full access is what the *sandbox* grants and a request to go beyond it is still unanswerable. Each refusal is logged at WARNING with the method, the runtime and the agent kind, because a silently refused escalation and a model that simply chose not to try look identical from the outside.

**There is no `"deny"` decision in this protocol.** Each method spells refusal its own way, and `CodexClient._reader_loop` writes whatever the handler returns straight back as the JSON-RPC `result`, so a plausible-looking guess is a protocol violation on the wire. The five approval methods in the `ServerRequest` union, with the values read out of the schema the shipped binary generates (`codex app-server generate-json-schema`):

| method | refusal | notes |
|---|---|---|
| `item/commandExecution/requestApproval` | `{"decision": "decline"}` | `decline` = refused, the agent continues the turn; `cancel` would refuse *and* interrupt the turn |
| `item/fileChange/requestApproval` | `{"decision": "decline"}` | same vocabulary |
| `item/permissions/requestApproval` | `{"permissions": {}}` | not a `decision` at all — the response is a granted-permission profile, whose `fileSystem` and `network` are both optional, so `{}` grants nothing |
| `execCommandApproval` (legacy) | `{"decision": {"denied": {"rejection": …}}}` | the older `ReviewDecision`, which also has two refusals: `abort` ("do nothing until the user's next command") and `DeniedReviewDecision` ("should not execute it, but it should continue the session and try something else"). `denied` is the legacy analogue of `decline`, `abort` of `cancel` |
| `applyPatchApproval` (legacy) | `{"decision": {"denied": {"rejection": …}}}` | same |

A refused escalation is not a turn failure: the agent should be left to finish with what the sandbox already allows. Four of the five vocabularies put that as a choice — a refusal that stops the turn, and a refusal that lets the agent carry on — and each of those four rows picks the second. `item/permissions/requestApproval` offers no decision at all, its response being a granted-permission profile rather than a verdict, so refusing it means granting nothing and the agent carries on by construction.

`denied` is also the one refusal in the protocol that carries text back to the model, and that text is the reason to prefer it over `abort`: an agent told *why* it was refused and what it may still do can adapt, where one told only "no" cannot. Both legacy methods send the same string, from a single module constant (`_LEGACY_REJECTION`). It is model-facing, so it is written in the agent's terms — that the agent runs unattended, that no one can be asked, and that it should continue within the sandbox — and carries no BOS vocabulary and no section numbers.

Two further properties of the seam constrain the handler. It is handed **every** server-to-client request, not only approvals: the other five (`item/tool/call`, `item/tool/requestUserInput`, `mcpServer/elicitation/request`, `attestation/generate`, `account/chatgptAuthTokens/refresh`) fall through to `{}`, exactly as the vendor default answers them, and widening that is out of this section's scope. And it is **synchronous**, called on the vendor's single stdout reader thread rather than the event loop, so it must never block — that thread is the sole consumer of the child's stdout, and stalling it stalls every notification and every response for every turn.

The pinned test is what makes the private reach-in acceptable, and it is pinned in both directions: an SDK upgrade that moves the attribute breaks CI instead of quietly re-opening the hole, and one that adds a supported `approval_handler` parameter breaks CI to say the reach-in can stop. There is deliberately no `getattr` guard — a silently restored auto-accepting default is the entire hazard. That these refusals are *accepted* by a live `codex app-server` is only confirmable by a real run — a normal run reaches the two `requestApproval` methods; the legacy pair and the permissions profile are backstops a live run may never exercise. Asserted in §7 criterion 18 rather than claimed from CI.

**The approval policy is `never`, for every `permission`, and no LLM is in the loop.** Every Codex thread BOS starts uses `ApprovalMode.deny_all` — `AskForApproval(never)` with no approvals reviewer — so an escalation past the sandbox is refused by Codex itself, before the command runs, with its own message ("you cannot ask for escalated permissions if the approval policy is Never"), and the sandbox chosen from `permission` is the whole boundary. `_deny_approval` stays installed as the backstop it was meant to be: under `never` no approval request is expected to reach it, but a vendor path that asks anyway meets "no" rather than the auto-accepting default.

**This section used to say otherwise, and live validation found it.** The first version mapped `workspace-write` and `full-access` to `ApprovalMode.auto_review`, on the stated reasoning that `auto_review` is `on_request` "so the server asks only when the agent asks to escalate". It does ask — but not BOS. The SDK turns `auto_review` into `on_request` *plus* `ApprovalsReviewer.auto_review`, and that reviewer is an LLM guardian inside Codex (`thread_source: "guardian_review"`, model `codex-auto-review`) that judges the request against what the chat's user appears to have authorized. In a host app, the chat's user is whoever typed into it. Against the owner's real subscription, a `workspace-write` agent asked to write under `~/.cache/…` — outside `cwd`, outside `/tmp` — requested an escalation, the guardian returned `"outcome": "allow"` because "the user explicitly requested writing OK to this exact path", and the write went through. `_deny_approval` never saw the request. So the handler this section spent most of its length on was bypassed by construction for every permission except `read-only`, and the assumption that made it look sufficient — that `on_request` means "ask the client" — was never measured. The same run explained two other results: no escalation ever reached `_deny_approval` (§7.18), and BOS's MCP tool succeeded under `workspace-write` because the guardian granted the approval an unannotated MCP call needs.

The defect is now reproduced in CI without a login: `test_an_escalation_is_refused_by_codex_and_judged_by_nobody` drives the real `codex app-server` against a fake Responses-API model that asks for exactly that escalation and answers any reviewer request with the live rollout's own *allow* verdict. Under the old mapping the child makes a `codex-auto-review` request and the write lands; under `never` it makes none, refuses the command, and nothing is written. A `native_options.config` carrying `approval_policy` or `approvals_reviewer` does not reopen it — both lose to the typed `approval_policy = never`, measured — and `approval_mode` itself is reserved (§3.4).

`never` has one cost, and it is paid only for BOS's own server: an MCP tool call that needs approval is refused outright ("MCP tool call requires approval, but approval policy is never"), which is exactly what live validation's `read-only` agent hit. BOS therefore sets `default_tools_approval_mode = "approve"` on its `bos-tools` entry, and on nothing else (§3.8).

**Claude Code offers the same hazard under another name.** `permission_mode="auto"` has the CLI ask a classifier model before a tool runs — an LLM deciding, as `auto_review`'s reviewer did for Codex's escalations — and no `permission` maps to it (§3.5). Claude Code's confinement design was corrected by measurement too, before implementation rather than after (§3.5.3).

#### 3.5.5 Verification is behavioural

Per-runtime acceptance (§7.18) asserts observed effects — a write outside the root fails — not that a mode name was passed. Mode names are evidence of intent, not of enforcement.

It asserts only what each runtime actually bounds, and that is not symmetric. This section used to promise "a read outside the root fails" for both runtimes; that holds only for Claude Code's file tools.

| Outside `cwd`, under `read-only` or `workspace-write` | Writes | Reads |
|---|---|---|
| Codex | bounded by the sandbox, except that `workspace-write` may write `/tmp` and `$TMPDIR` by default (§3.5) | **not bounded**: neither `ReadOnlySandboxPolicy` nor `WorkspaceWriteSandboxPolicy` has a field that restricts reads (read from `openai_codex`'s generated schema); no live run attempted such a read |
| Claude Code, file tools | denied by the hook | denied by the hook |
| Claude Code, bash | `read-only`: `Bash` is denied by the hook, outright. `workspace-write`: failed by the sandbox, and a `touch` under `/tmp` did not reach the host's `/tmp` (fact 6b) | `read-only`: denied with the rest of `Bash`. `workspace-write`: **not bounded** — a `cat` of a file outside `cwd` returned it (fact 6b) |

Under `full-access` neither runtime bounds anything. Every "denied by the hook" above is the hook's design: the vendor facts measure its deny on `Write` alone (§3.5.3), and that it also denies reads, `Bash` under `read-only`, and every other file tool is what §7.18 asserts, per tool, once the hook is built. One bash write path is not measured at all: the CLI hands a sandboxed command a `TMPDIR` of its own choosing (read from source), and whether that directory is writable from inside the sandbox was not tested — so "a bash write under `/tmp` does not land" is measured only for a path directly under `/tmp`.

### 3.6 Session continuity

`ask(chat_id, …)` must resume the same native conversation on the next turn.

| | Resume | Id returned by |
|---|---|---|
| Claude Code | `ClaudeAgentOptions.resume = <session_id>` | `ResultMessage.session_id` |
| Codex | `AsyncCodex.thread_resume(thread_id)` | `AsyncThread.id` |

The mapping is stored in the **metadata of the assistant message BOS commits each turn** (§3.7): `{"external_runtime": "codex", "native_session_id": "…"}`. It is rewritten every turn, so the newest committed message always carries the freshest id; recovery after a restart is `chat_store.get_messages(chat_id)` scanned from the end. No new store, no `ChatStore` schema change, no separate mapping file. `read_native_session_id` re-runs that scan on every call; an in-process cache in front of it is not built (§8.2). A store that fails to read raises out of it rather than reading as "no session", which would start a fresh session under the same `chat_id` — the case the next paragraph rules out.

A native session that cannot be resumed — deleted, archived, pruned — is reported as an error naming the runtime and the id. BOS does not silently start a fresh session under the same `chat_id`. Claude Code refuses a `resume` it has no session for at startup, before any model call and without starting a session ("No conversation found with session ID: …"), which the SDK raises out of `connect()`; measured against CLI 2.1.281 and pinned in CI against the real CLI, and BOS reports that refusal, matched on the CLI's statement naming the id, as this error. Any other error result at startup is reported as a failure at startup with the CLI's own text instead, because calling it a lost session would send an operator looking for one (§3.10.2). A resumed Claude Code turn that comes back on a session id other than the one it resumed is refused too, committing nothing: measured, a resumed turn answers from the session it resumed, and the SDK documents a new id only under `fork_session`, which `native_options` refuses.

Changing an established chat's runtime starts a new native session and says so (§2.2.4). The newest committed message that names an external runtime decides: when it names another runtime, `read_native_session_id` logs a WARNING naming the chat, that runtime and the one asking, and answers "no session", so the turn starts a new one. A chat that switches back is therefore not handed the session it left — codex, then claude-code, then codex again starts a new Codex thread, since the old one has not seen the Claude Code turns in between.

### 3.7 What BOS persists, and `BosApp.get_messages`

BOS commits **two messages per turn**: the user message, and the final assistant text with the metadata from §3.6 plus `{"usage": …, "native_turn_id": …}`. It does not commit the native runtime's tool calls, tool results, or thinking. Codex's `native_turn_id` is its turn id. Claude Code's stream names no turn, so its `native_turn_id` is the uuid of the turn's last top-level assistant message — a transcript entry, which `get_session_messages` returns under that uuid (pinned in CI against the real CLI); `ResultMessage.uuid` is in no transcript, and the prompt's own entry is not in the stream (both measured against CLI 2.1.281, not pinned).

That thin record is what `AgentActor`, `AskSubagent`, memory ingestion and `list_chats` see, and it is the only part BOS guarantees. Intra-turn activity reaches a live UI through `event_sink` (§3.9), not through the store.

The full transcript is read on demand from the runtime that owns it. A new method on `BosApp` — the one place a host asks for messages without knowing which runtime produced them:

```python
async def get_messages(self, chat_id: str, *, source: Literal["auto", "bos", "native"] = "auto") -> list[Message]: ...
```

- `source="bos"` — `harness.chat_store.get_messages(chat_id)`. Unchanged behaviour, always available.
- `source="native"` — delegates to `native_messages(chat_id)` on the runtime that owns the session. Claude Code: `get_session_messages(session_id, directory=…)`, which parses the JSONL under `~/.claude/projects/` and chains it by `parentUuid`. Codex: `thread.read(include_turns=True)`, on an `AsyncThread` constructed directly over the client — never `thread_resume`, which would re-establish a live session with this agent's sandbox, approval mode and `cwd` on what the caller asked to be a read. Both project into BOS `Message` objects (`role`, `content`, plus `metadata["source"] = "<runtime>"`, `metadata["native_turn_id"]`, and `metadata["native_item_id"]` for a message projected from a transcript item) so a host's rendering code does not fork. A gap marker (below) is not projected from an item and carries no `native_item_id`; the turn id is the handle a host has on it.
- `source="auto"` — read the BOS record, and if its metadata names an external runtime, return the native transcript; otherwise return the BOS record.

**Messages only, and only the ones a conversation is made of.** Codex's `ThreadItem` is a nineteen-member union; two of them — `UserMessageThreadItem` and `AgentMessageThreadItem` — are messages, and the other seventeen (reasoning, command execution, file change, MCP tool call, web search, plan, the inline `ContextCompactionThreadItem`) are the turn's internal work. They are skipped, and a native read carries no `tool_calls`, for a structural reason and not merely a stylistic one: **BOS represents tool activity as a pair** — an assistant message advertising `tool_calls`, then a `role="tool"` message whose `tool_call_id` matches it — and a native transcript has no such pairing. Projecting a `CommandExecutionThreadItem` into that shape means inventing a call id and an assistant message the runtime never produced, which a host renders as authoritative rather than as a reconstruction. That is a forgery, not a projection, and it is the reason this is settled rather than a matter of effort.

**And BOS does not have that activity anywhere else.** `event_sink` (§3.9) is a live stream emitted while BOS itself runs a turn; nothing under `bos/core/` persists it, and for the case `source="native"` exists for — a session BOS did not author — none was ever emitted. So the honest statement to a host is that the tool activity is unavailable through BOS, not that it is available on another surface. A host that needs it reads the runtime's own store with the runtime's own tools.

Among agent messages, `final_answer` and no-phase are kept and `commentary` is skipped — the same rule the turn path's own `_final_assistant_response_from_items` applies, for the same reason: commentary is not the answer.

**A turn the runtime did not load becomes a visible gap, not a shorter list.** Codex's `Turn.items_view` is `notLoaded | summary | full`, and on anything but `full` the turn's `items` are absent or summarized. Projecting them anyway would publish a shorter conversation than the one that happened, which is exactly the silent lie this section exists to prevent; dropping the turn would do the same more quietly. So each such turn emits one marker `Message` carrying `metadata["items_view"]` and logs at WARNING, and the read still succeeds — a partly-unloaded old thread is ordinary, and raising would break the read for exactly the long-lived sessions someone wants to read.

**Routing is by stored metadata, not by a `chat_id` naming convention.** The `external_runtime` key is already required for §3.6, so the lookup costs nothing extra, it works for chat ids a host created before this BEP, and it avoids a second id convention colliding with the existing one (`INTERNAL_CHAT_SEPARATOR = "~"`, shape `{parent}~{tag}~{uuid}`, [`_chat_store_utils.py:12-38`](../../src/bos/core/_chat_store_utils.py)). Which *agent* speaks for that runtime is decided by matching `resolved_config["external_runtime"]` against it, and never guessed: no built agent for the runtime, more than one, or one with no `native_messages` each raise, naming the runtime and what to do, rather than reading the wrong transcript or falling back to the BOS record — which would answer a different question than the one asked. `native_messages` is duck-typed rather than added to `AgentPort` or `ExternalRuntime`, because only a runtime with a transcript of its own can offer it and widening either protocol would oblige BOS's own `Agent` to implement it.

`ChatStore` is **not** modified and not wrapped. A host reading `app.harness.chat_store.get_messages(chat_id)` directly — which is what the first host does today, and the only public path, since `Agent` exposes no `chat_store` property — keeps getting exactly what it gets now: the BOS record. `app.get_messages` is additive.

**What `source="native"` does not promise.** It is a live read of data BOS does not own. Each runtime compacts and prunes on its own schedule; a Codex thread can be archived or deleted; Claude Code's transcripts live under the invoking user's `~/.claude/projects/` and move with that home directory. `items_view` can come back partial. So a native read can return fewer messages than it did before, can contain gap markers where the runtime declined to load part of its own history, or can fail. `source="bos"` is the only read BOS stands behind. The known upgrade path for Claude Code is `ClaudeAgentOptions.session_store`, an official port whose contract is *"every transcript line written locally is also passed to `session_store.append()`, and `resume` can materialize from the store when the local file is absent"* — implementing it over `.bos/` would make transcripts workspace-local and portable. Not in this BEP. Codex exposes no equivalent port.

### 3.8 The MCP egress

A host application's own API is registered as BOS tools via `ep_tool`. A BOS agent calls them directly. An external runtime cannot: it has its own tool loop in another process. MCP is the only wire either vendor offers, and both accept **streamable HTTP**:

- Claude Code: `McpServerConfig` is `McpStdioServerConfig | McpSSEServerConfig | McpHttpServerConfig | McpSdkServerConfig`; the HTTP form is `{"type": "http", "url": …, "headers": {…}}`.
- Codex: `[mcp_servers.<name>]` supports STDIO and Streamable HTTP with `url`, plus `bearer_token_env_var` / `http_headers` / `env_http_headers`. `AsyncCodex.thread_start(config=…)` injects config overrides per thread.

So there is **one server, not one per vendor**:

- `BosToolMcpServer` ([`mcp_egress.py`](../../src/bos/extensions/runtimes/mcp_egress.py)) builds an [`mcp.server.lowlevel.Server`](https://github.com/modelcontextprotocol/python-sdk), not the higher-level `mcp.server.mcpserver.MCPServer` an earlier draft of this section sketched: `MCPServer.add_tool` has **no schema parameter at all** — it derives a tool's input schema by introspecting the Python function it wraps — so a generic `**kwargs` closure forwarding to `ep_tool.invoke(name, kwargs)` would advertise a tool that takes no arguments, never the host tool's real JSON schema. The lowlevel `Server` is constructed with `on_list_tools=` / `on_call_tool=` handlers that build `types.Tool` / `types.CallToolResult` objects directly, so `ep_tool.build_openai_schema(ext)`'s schema reaches the client unmodified.
- **Per-agent scoping cannot be an HTTP middleware**, and the earlier draft's sketch of one was the section's central error: a middleware sees a request and a response byte-stream, never the MCP-level `tools/list` *response body* it would need to filter — every agent would have seen every tool. Instead, `on_list_tools`/`on_call_tool` each read the caller's bearer token off `ctx.request.headers` (`ServerRequestContext.request`, `Optional[Request]`) and compute that call's allowed tool set themselves, so the listing *for that call* already **is** the allowlist. This works because `mcp` 2.x's streamable-HTTP session runner attaches the inbound Starlette `Request` to *each dispatched message* (`mcp/server/streamable_http.py`'s `_message_metadata`, read back out in `mcp/server/runner.py`'s `_make_context`), not to the connection — so a single kept-alive HTTP connection carrying many calls still gets the right grant on every one of them, even interleaved across agents. `ServerRequestContext.request` is marked transitional upstream (`# TODO(L54): remove for Context rework`); `mcp_egress.py`'s `_headers_of` is the one place that reads it, annotated as `ServerRequestContext[Any, Request]` so pyright — not just a runtime probe — catches the day it moves. (`ServerRequestContext` takes two type parameters; the second, `RequestT`, defaults to `Any`, so annotating only `[Any]` would leave `ctx.request` unchecked.)
- The app actually served is `Server.streamable_http_app(streamable_http_path="/mcp", stateless_http=True, host="127.0.0.1")` under an in-process `uvicorn.Server` on an ephemeral loopback port, run via `config.load()` / `server.startup()` / `server.main_loop()` rather than `Server.serve()` — the latter installs `SIGINT`/`SIGTERM` handlers on the thread it is called from, which belongs to whatever embeds BOS. `streamable_http_app` is a method both the lowlevel `Server` and the higher-level `MCPServer` expose under the same name; naming `MCPServer` for it was an easy mistake given that, but the object actually serving requests is the lowlevel one built two bullets up.
- A raw ASGI wrapper (`_gate`, not Starlette's `BaseHTTPMiddleware` — that buffers through a wrapping response and does not get along with the transport's SSE streams) sits in front of the app and fails closed: every ASGI scope except `lifespan` (which carries no headers and is how the MCP session manager itself starts up) must present a bearer token from a prior `register_agent()` call, including a `websocket` scope this app registers no route for — refused with a 401 over HTTP or a `1008` close over that scope, never silently proxied through. A token is never written to config or to a transcript; Codex receives it through `bearer_token_env_var` plus `CodexConfig(env=…)` — see the paragraph below for why not `http_headers`, which an earlier round of this shipped — and Claude Code through `headers: {"Authorization": "Bearer ${BOS_MCP_BEARER_<random>}"}` with the value only in `ClaudeAgentOptions.env`. A literal token in `headers` would not do: the SDK puts `mcp_servers` on the CLI's command line as `--mcp-config` JSON (`subprocess_cli.py:682`), which other local users can read from `/proc/<pid>/cmdline`. The CLI expands `${VAR}` in an HTTP server's headers from its own environment, so the placeholder rides the command line, the value only the child's environment, and the server receives `Bearer <value>` — fact 7 (§3.5.3) asserts all three. The value then rests in the child's environment, same-user readable: the same trade as Codex's, below — though whether the agent's own shell can read it, as Codex's could, is not measured for Claude Code.
- Claude Code's in-process `create_sdk_mcp_server()` is deliberately **not** used: it would be cheaper for Claude and unusable for Codex, producing two tool-serving code paths. A Codex stdio shim is also rejected — a shim process still needs IPC back into BOS, and HTTP *is* that IPC.
- Every Claude Code client is built with `strict_mcp_config`, so the CLI loads only the MCP servers BOS passes it: a repository's `.mcp.json` server started without it and did not start with it (measured, §3.5.3). Whether it also keeps out servers from the operator's own Claude Code config was not measured.

For Codex the endpoint is injected per thread, not per process: `thread_start`/`thread_resume` take a `config` object that is merged over `~/.codex/config.toml`, and BOS passes `{"mcp_servers": {"bos-tools": {"url": server.url, "bearer_token_env_var": "BOS_MCP_BEARER_<random>", "default_tools_approval_mode": "approve"}}}` with the token itself in `CodexConfig(env=…)`. The server name is one constant (`_MCP_SERVER_NAME`), and it is `bos-tools` — what the server already calls itself over MCP — rather than the bare project name, because the merge means it is shared with the operator's own config and a collision is a real failure (§8.2).

Which auth key carries the token is a security choice, not a style one, and it was settled by driving the real `codex app-server` against a loopback server that records the `Authorization` it receives. `bearer_token_env_var` is the one whose token the child actually sends, against every credential key such an entry can carry. The enumeration is the binary's own rather than the set of things tried — `codex mcp get <name> --json` renders a loaded streamable-HTTP `transport` as exactly `url`, `bearer_token_env_var`, `http_headers`, `env_http_headers`, `http_headers_helper` — and each of the four credential keys was planted on a colliding operator entry and lost, as did no operator entry at all. One path is outside that enumeration and **unmeasured**: OAuth, which is a mechanism rather than a key (`codex mcp add --oauth-client-id/--oauth-client-registration/--oauth-resource`, credentials supplied by `codex mcp login`), and which measuring needs a provider. `http_headers` — which an earlier round shipped — loses to an operator `bearer_token_env_var`, and losing is silent (§8.2). `bearer_token` is not a literal-token key at all and fails config loading outright. The variable name is generated fresh per client so that no other `[mcp_servers.*]` entry can name it and read BOS's token out of the shared environment; `CodexConfig(env=…)` is additive, so the child keeps the rest of its environment. The cost is that the token rests in `/proc/<pid>/environ`, same-user readable — worse than a JSON-RPC message, better than the `--config` command line — and, observed in live runs 2 and 3, it is present in the agent's own shell: `env | grep -c '^BOS_MCP_BEARER'`, run by the agent, counted it. The value itself was deliberately not printed. What it can do with it is call the tools already in its own grant, no more, since the server scopes every request by that token.

It is built once, inside `_ensure_client`, so an agent that never runs a turn never asks the harness for a server at all. Nor does one with nothing to serve, and that is two cases rather than one: an empty `mcp_tools`, and an `mcp_tools` whose every name the host has no `ep_tool` for. The runtime settles the second itself, by asking the same `unregistered_tools` predicate `resolved_config` uses — no server needed — so it can emit the §7.5 warning *and* decline to bind a port, which are only compatible because the rule is a predicate rather than something the server decides. It hands `register_agent` only names that already resolve, so `register_agent`'s own warn-and-skip does not fire a second time on this path; that warning stays as the safety net for any other caller.

`default_tools_approval_mode = "approve"` is there because every Codex thread runs with the approval policy at `never` (§3.5.4), and `never` refuses any MCP call that needs approval. It is established from the binary rather than from its name: the key's own error enumerates its values (`unknown variant …, expected one of auto, prompt, writes, approve` in `mcp_servers.<name>.default_tools_approval_mode`), and driving the real child with a fake model under `never` showed that `approve` lets a `bos-tools` call complete while `auto`, `prompt` and `writes` all still fail, and that it is scoped to the one server — a second MCP server the operator configured was refused in the same turn. It is server-wide rather than per tool (`tools.<name>.approval_mode` exists and works too) because this server's `tools/list` already *is* the grant, per bearer token, and calls outside it are refused server-side; approving everything it lists is approving exactly the grant. `enabled_tools` was measured to hide an unlisted tool and is deliberately not set: it would be a third copy of the grant, and how it matches names against Codex's normalization (the namespace is already `mcp__bos_tools`, hyphen folded) was not measured. `codex mcp get --json` does not render `default_tools_approval_mode` at all, so that view is not a complete listing of an entry either.

Selection is one list, resolved against the global `ep_tool` registry by name:

```toml
mcp_tools = ["DeskCreateTask", "DeskGetOrder"]   # default []; "*" is not accepted
```

A name with no matching `ep_tool` entry is a `logger.warning` naming the agent and the name, and is skipped — a host that renames a tool gets a visible line, not a startup crash. An empty list means no MCP server is started for that agent at all.

There is **no registration-time `mcp_exportable` flag**. Exposure is a deployment decision, the list is explicit, and a second gate at registration would only add a way for the two to disagree.

**No automatic de-duplication against native tools, either.** The list is explicit: not writing `Bash` or `WebSearch` is what keeps them out. Guidance, not mechanism: expose the host's domain API, and leave file, shell, and web search to the runtime's own tools, which are already good and already covered by the subscription. Detecting "overlap" across two vendors' tool vocabularies would be guesswork.

Tool execution stays in the BOS process, under BOS's own tool implementations. The MCP server is an entry point, not a second execution path.

**The event stream does not tell a host which message is Codex's commentary and which its final answer.** Both arrive as `response`/`finish` `TurnEvent`s carrying the message text and nothing that says which is which: Codex marks each agent message with a phase (`commentary`, `final_answer`), and `_event_for_notification` does not forward it. Observed in live runs 2 and 3 — an ordinary read-a-file turn emitted `response/finish`, a `tool` start/finish pair, a second `response/finish`, then `turn/finish`. `AgentResult.output` is unaffected: it is the final answer, chosen by phase. It is only the live stream that is ambiguous.

**Claude Code has no commentary/final-answer phase at all — not even the ambiguous kind Codex has.** Every assistant `TextBlock` becomes its own `response`/`finish` `TurnEvent`, with nothing to omit the way `_event_for_notification` omits Codex's `MessagePhase`, because the CLI reports no phase on a message to begin with. A host that wants *the* answer, not *a* response, reads `AgentResult.output` (`ResultMessage.result`, via `run()`'s return value) — never the stream — since the ordinary `turn`/`finish` event carries no content of its own and nothing in the stream is marked authoritative. Two message shapes that look like tool events are deliberately not: the CLI's synthetic `StructuredOutput` tool call, which `schema=` makes the CLI offer to the model and answer itself (the `output_format` paragraph below) — the agent never chose to call it, so `_events_for_message` never turns its `ToolUseBlock` into an event and never records its id, so the matching `ToolResultBlock` later matches nothing and is skipped the same way any other untracked id would be, with no check on the tool's name at that end — and the CLI's own one-shot `"[structured-output-enforce]"` nudge, a plain-text `UserMessage` that maps to nothing because only `ToolResultBlock` is ever matched inside a `UserMessage` at all. A turn that ends on `max_turns` (`ResultMessage.subtype == "error_max_turns"`) emits `turn`/`fail` instead of the ordinary `turn`/`finish` — `stage` and `detail` both `max_iteration`, `content` the static `MAX_ITERATION_CONTENT` marker, `metadata` carrying `max_iterations` (`options.max_turns`) and `closure_reason` (`"max_iterations"`) beside whatever `ctx_metadata` the caller supplied — mirroring what BOS's own `Agent` emits at `_close_with_handoff("max_iterations")` (`agent.py`). Of that call's own metadata keys, `iteration` and `handoff` are left out rather than forced to a value that would always be the same one: BOS does not see the CLI's own internal turn count the way `Agent` counts its own loop, and no external runtime is ever handed a consolidator, so `handoff` could never be anything but `False`. A schema retry re-enters this same per-message loop on a fresh `receive_response()` round on the same connected client, so every attempt streams its own tool/response/turn events, not just the winning one — the same shape `CodexAgent`'s own retry loop produces, since each of its retries is a new native turn run through `_run_turn`/`_emit_stream` in full.

The `interrupt` rows are split because the callback's **name is not its meaning**, and conflating the two is a live source of inverted implementations. It is a poll, and its *return value* is a message to merge into the turn that is still running (`Agent._interrupt`: `ctx.add_message(llm_message, merge=True)`); `AgentActor._make_interrupt` returns exactly that for a queued `INTERRUPT_MESSAGE`, a user's follow-up sent mid-turn. Stopping is a different signal entirely — a raised `AbortTurn`, or `request_stop()` — never a truthy return. Two consequences the earlier one-row form hid: reading the row as "fires → stop" kills the user's follow-up instead of delivering it (Codex Layer 4a shipped that and had to be fixed), and the poll is **destructive** — it pops the pending envelopes — so a runtime must not poll once its turn has terminated, or it takes a message it can no longer deliver.

**How a message reaches a running Claude Code turn was measured against CLI 2.1.281 with the fake Messages API before it was built, and it is why the truthy-return row reads as it does.** `client.query()` sent while `receive_response()` is still iterating starts no turn: the CLI queues the message and, once the tool calls of the model's next response have run, folds it into the following model request, wrapped in the CLI's own "The user sent a new message while you were working: … This is how Claude Code surfaces messages the user sends mid-turn — within the running turn, often alongside the next tool result, rather than as a separate conversation turn." The turn goes on, and one `ResultMessage` ends it. That holds only while a model request is still to come. A message that arrives after the turn's last model request has gone out — while the final answer is produced, or before a response with no tool call — misses the fold, and the CLI runs it as a native turn of its own right after the `ResultMessage`; read from source, a message with no `priority`, which is what the SDK sends, ranks as `next`, folded after a tool batch and otherwise kept for the next turn. Left unread, that turn would still run — the CLI also runs a queued message when stdin closes — so BOS reads it as part of the same BOS turn: its events stream, its answer is `AgentResult.output`, its session entry is `native_turn_id`, and its usage is added to the first turn's. The first turn's `ResultMessage` emits no `turn` event: one BOS turn has exactly one `turn`/`finish`, which a host may take as the end of the turn. BOS tells the two cases apart because every client is started with `--replay-user-messages`, a flag the SDK documents as an `extra_args` value: the CLI echoes each message BOS sends, with the uuid BOS put on it, when it takes the message into a turn — before the `ResultMessage` when it was folded in, after it when it runs as its own turn. A stop drops a message still queued, because a bare interrupt does not: the message outlives it and runs as a turn nothing reads. The `interrupt` control request takes `cancel_queued` for that — read from the CLI's source, where the SDK client bundled with it sends it as `interrupt({cancelQueued: true})` — but `ClaudeSDKClient.interrupt()` sends a bare one, so BOS sends the request through the SDK's private `Query._send_control_request`, and `test_the_interrupt_reaches_the_cli_through_an_sdk_path_that_still_exists` fails when that path moves or when `interrupt()` gains an argument. An interrupted turn ends as an error result — subtype `error_during_execution`, `is_error`, no `result`, `terminal_reason` `aborted_tools` while a tool ran or `aborted_streaming` while the model answered — which BOS keeps as a partial answer only for a stop it sent itself; any other interrupted result is raised like every error result. A message the poll returns once a stop has begun, one BOS fails to send, and one a stop drops from the CLI's queue are each logged at WARNING, since each came from a user and nothing else records it. Pinned against the real CLI: the fold, the turn of its own, the queued message a stop drops, and `aborted_tools` (`tests/test_claude_code_runtime.py`); `aborted_streaming` and the run on stdin closing were measured, not pinned.

`AgentResult` is populated from `ResultMessage` or `TurnResult`, and `finish_reason` carries the native terminal reason verbatim. From `ResultMessage`: `result` → `output`; `terminal_reason`, or `stop_reason` when the CLI reports none, → `finish_reason`; `usage` → `usage`, under the keys Codex reports, each meaning what it means there — so `input_tokens` counts every input token, the cache's reads and writes among them, where Anthropic's leaves both out — and the keys with no counterpart are not carried (`claude_code._usage` lists them). The counts are the turn's, summed over its model calls (measured). `total_cost_usd`, `model_usage` and `num_turns` are **dropped**: `AgentResult` has no field for a cost, and its `iterations` is 1 for every external turn. `max_turns` is a budget, not an error: a turn that spends it, which the CLI ends as an error result with subtype `error_max_turns` (pinned in CI against the real CLI), closes as BOS's own `Agent` closes at `max_iterations` — `output` is `MAX_ITERATION_CONTENT`, with no handoff, since nothing hands an external runtime a consolidator; `finish_reason` is the CLI's, verbatim (`max_turns`); and its two messages are committed with the turn's session id, so the next turn resumes the session that ran it. Any other `ResultMessage` with `is_error` is raised with its `subtype`, `errors`, `api_error_status` and `result`, and nothing is committed. From `TurnResult`: `usage` → `usage`, `status` → `finish_reason`. `TurnResult.error` and `.duration_ms` are **dropped** — `AgentResult` has no field for either — and the first costs nothing, because a failed turn never reaches this path: the vendor raises before constructing a `TurnResult`, and BOS re-raises with that message.

**What `options.output_format` makes the CLI do to the model was measured against CLI 2.1.281 with the fake Messages API, not assumed, and it is why the `schema` row names `result`, not `structured_output`.** The CLI offers the model a synthetic `StructuredOutput` tool — its `input_schema` is exactly the schema BOS sent — and answers a call to it itself, with a synthetic tool result ("Structured output provided successfully"), rather than ever handing BOS a tool call to run; `ResultMessage.result` then is that tool call's JSON input, compact, verbatim, and `ResultMessage.structured_output` is the same value already parsed. If the model replies without calling the tool, the CLI injects its own one-shot nudge — a `UserMessage` reading `"[structured-output-enforce] You MUST call the StructuredOutput tool to complete this request. Call this tool now."` — and tries once more, inside the *same* `query()`/`receive_response()` round trip: BOS always sees exactly one `ResultMessage` per attempt, whichever way it went, and if the model still does not comply the turn still ends as an ordinary success, `is_error=False`, with `structured_output=None` and `result` whatever text the model last gave. None of that is trusted on its own (BEP 12): `ClaudeCodeAgent.run` re-validates `result.result` locally with the injected `StructuredValidator` regardless, the same one code path whether or not the tool was called, and a validation failure sends one plain-text correction message per retry as a new `query()` on the *same* connected client and native session — not a new CLI child. Measured: `max_turns` is a budget that resets for every `query()`, so a retry gets the same fresh budget the first attempt did, as it gets a `timeout_seconds` window of its own (§3.10.2); and because the CLI's self-correction nudge above already spends a native turn, `max_turns=1` with `schema` set exhausts on the very first attempt whenever the model does not comply immediately, before BOS's own retry loop ever runs. A turn that spends `max_turns` — first attempt or a retry — is never schema-checked: it closes exactly as any other turn that runs out does (the paragraph above), unstructured, mirroring the same call BOS's own `Agent.run` makes for a schema turn that hits `max_iterations` — `_close_with_handoff` never sets `structured_ok` (`agent.py`) — rather than raising `StructuredOutputError` for an answer the model was never given the budget to produce.

**Dropped on purpose**, with one `logger.debug` line at construction listing whichever were set: BOS `tools` / `exclude_tools` (the runtime has its own; the host's reach it via §3.8), BOS plugins, `consolidator` and all compaction, `interceptor`, `max_tokens`, `tool_noise_filter`, `history_attribution`. None of these has a counterpart, and forwarding them would be a lie about what the runtime honours. `max_iterations` is deliberately not in this list, because the row above forwards it to Claude Code's `options.max_turns`, and that is now built: `ClaudeCodeAgent.__init__` takes `max_iterations` out of its config before handing the rest to `parse_external_config`, and sends it as `max_turns` — refused unless a positive integer, since the SDK sends no limit at all for 0. The shared `_DROPPED_KEYS` still lists it, so the drop fires only for Codex, which has no counterpart; its comment now says so.

### 3.10 Lifecycle, concurrency, timeouts, auth

#### 3.10.1 Clients and concurrency

Codex: one `AsyncCodex` per `CodexAgent`, started lazily, owning one `codex app-server` child; threads are per `chat_id`. Claude Code: one `ClaudeSDKClient` per turn with `resume=`, disconnected in `finally`.

```python
# ponytail: a client per turn costs one CLI spawn (~1s). A per-chat_id session pool
# is the upgrade if that latency shows up; resume= makes the stateless version correct.
```

Two concurrent turns on one `chat_id` are rejected with a busy error rather than queued — the native session is single-threaded and BOS does not hide that.

#### 3.10.2 Timeouts and shutdown

`timeout_seconds` wraps the turn in `asyncio.timeout`; on expiry the native turn is interrupted, then the error is raised.

Every wait that a wedged child could otherwise use to hold a **shutdown** open is bounded. Two of them are RPCs the child answers at its leisure — the interrupt request and the `auth = "subscription"` preflight — and for both, guarding against *errors* is not the same as bounding against *slowness*: each sits on a queue read with no timeout of its own, so a child that never answers simply never returns. The preflight's bound is separate and much more generous than the teardown graces, because it is a credential check against a live service and a slow but working login must not trip it. Closing the client bounds itself (the vendor terminates, waits, then kills). Thread setup (`thread_start` / `thread_resume` / the turn request) runs before the turn's `asyncio.timeout` window exists, so each of those calls carries `timeout_seconds` itself, and a setup timeout names its phase so it is never mistaken for a turn that timed out while streaming — in particular, a wedged child on the resume path is **not** reported as the session-continuity error of §3.6, which would send an operator looking for a corrupt session. A setup timeout interrupts nothing, and on the turn request that is a limitation rather than a saving: the native turn may already be running and BOS cannot stop it (§8.2, *An orphaned Codex turn*). It ends when the client closes, which is the honest limit of the sentence below.

`timeout_seconds` bounds **one native turn attempt**, not the whole `run()` call. That is what it already meant: each schema-validation retry gets its own fresh window, so a retried turn can take a multiple of it. Extending the same per-attempt bound to setup is consistent with that; making it a whole-call deadline would be a different promise and is deliberately not made. With `timeout_seconds` unset there is no bound anywhere, because the caller declined one — a wedged setup is still recoverable, since no turn task is registered yet, so `aclose()` takes the uncontended client lock and closing the client fails the pending request.

**Claude Code's waits are different ones, bounded to the same rules, and audited once in `claude_code.py` above `_Turn`.** `connect()` — the CLI starting and, on a resumed chat, loading the session — carries `timeout_seconds` itself, a window of its own as each Codex setup call has, and its `TimeoutError` says "at startup", so a CLI that never finishes starting is not mistaken for a turn that timed out nor, on a resumed chat, for §3.6's lost session. No turn has started then, so nothing is interrupted; the SDK closes the half-started CLI itself on the cancellation. The SDK bounds `connect()` besides — its version probe under 2 seconds, its initialize handshake under `max(CLAUDE_CODE_STREAM_CLOSE_TIMEOUT / 1000, 60)` seconds (read from source) — which is what bounds it when `timeout_seconds` is unset. It is not raced against a stop: a stop that lands while the CLI starts takes effect when `connect()` returns, and the call returns `SHUTDOWN_CONTENT` without starting a turn. The interrupt is a control request the CLI answers at its leisure, and the SDK's own wait for the answer is 60 seconds, so BOS bounds it by the grace Codex's interrupt has. `disconnect()` bounds itself for the options BOS sends: the SDK waits up to 5 seconds for its write lock, closes stdin, waits 5 seconds for the CLI to exit, then sends SIGTERM and waits 5 more, then SIGKILL and 5 more — about 20 seconds at worst, the SDK's own figure (read from source, not measured). BOS never wraps it in a timeout, because an asyncio cancellation delivered inside it skips that escalation, as the SDK's docstring warns, and runs it shielded in a task of its own, so a caller that cancels the turn — `AgentActor` does, when a user aborts one — cannot land there either. A cancelled turn still tells the CLI to stop before closing it.

`aclose()` sets the same one-way stop flag `request_stop()` does, so a turn started afterwards returns `SHUTDOWN_CONTENT` with empty `usage` before any vendor call — observed in live runs 2 and 3. CI asserts the same pre-flight through `request_stop()`, which sets the same flag. `aclose()` asks every in-flight turn to stop, gives them a bounded window to drain, then closes the client regardless — closing the client is what reaps the child, so it must not be reachable only on the happy path. Claude Code has a client per turn rather than one per agent, so there `aclose()` closes every in-flight turn's client at once, through the same once-only disconnect the turn's own teardown uses, one failing close leaving the others to finish; a turn whose CLI is still starting has no client to reach yet — closing one mid-start could leave the CLI running — and closes its own when `connect()` returns, bounded as above. This is a bounded drain, not a guaranteed one: a turn that ignores both the interrupt and the cancel is abandoned to the event loop (the same doctrine as `Agent._abandon`) and reported in a warning naming how many were left. What the child is doing does end, because the client closes; what BOS cannot promise is that the in-process task tracking it has finished first, or — for a turn orphaned by a timed-out turn request (§8.2) — that anything short of closing the client could have stopped it sooner.

#### 3.10.3 Auth

`auth = "subscription"` (default) means the native runtime's existing login. Codex preflights it by calling `AsyncCodex.account()` and fails when no account is present — **on the first turn, not at `create_agent`**, and once per agent rather than once per turn. It cannot be at construction: the check is an RPC to the `codex app-server`, so running it there would spawn the child that §3.1 says is built lazily. `create_agent("codex")` therefore succeeds with no login and the first `ask()` is what fails, which is where an operator should be told to look. Claude Code's check is of a different kind and runs **at construction**, which it can because it only reads the environment and spawns nothing: `create_agent` refuses `auth = "subscription"` when any variable that makes the CLI stop using the subscription login is set in BOS's `os.environ` — which the CLI inherits whole (§3.12) — naming each one, what it does, and `auth = "api_key"`. They do not all do the same thing: most move the run onto another credential or provider, which then bills; one switches the login off; one only moves where the CLI looks for credentials. The list is enumerated from the CLI 2.1.281 source, from the two functions that decide it — the provider resolver, where anything but first-party bills elsewhere, and the predicate for whether the claude.ai login is used at all:

| Route | Variables | What the refusal says it does |
|---|---|---|
| A first-party credential used instead of the login | `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_API_KEY_FILE_DESCRIPTOR` | bills that credential instead |
| An `ant` profile, or OIDC federation | `ANTHROPIC_PROFILE`; `ANTHROPIC_FEDERATION_RULE_ID` with `ANTHROPIC_ORGANIZATION_ID` | bills the profile's credentials, or the federated organization, instead |
| Where the CLI looks for `ant` profiles | `ANTHROPIC_CONFIG_DIR` | moves where it looks for credentials it can use instead of the login |
| Requests through a local socket | `ANTHROPIC_UNIX_SOCKET` | bills whatever credential serves the socket |
| Bare mode | `CLAUDE_CODE_SIMPLE` | switches the login off |
| Another provider | `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`, `CLAUDE_CODE_USE_ANTHROPIC_AWS`, `CLAUDE_CODE_USE_ANTHROPIC_GOOGLE_CLOUD`, `CLAUDE_CODE_USE_MANTLE`, `CLAUDE_CODE_USE_GATEWAY` | moves the run to that provider (named by the CLI's own label), billed there instead |

Any non-empty value is refused, which is conservative where the CLI is stricter: it reads the provider flags as booleans, starts federation only with both of its variables, and uses a profile only if the profile store holds one. An empty value is not refused — every read of these in the CLI source trims or tests truthiness, or both. Examined and not refused: `CLAUDE_CODE_OAUTH_TOKEN`, which is a subscription token (what `claude setup-token` makes for a headless login); `ANTHROPIC_BASE_URL`, which changes where requests go but is not among the predicate's inputs; and the per-provider credentials and targets (`AWS_BEARER_TOKEN_BEDROCK`, `ANTHROPIC_VERTEX_PROJECT_ID` and the like), which the CLI reads only once a flag above has chosen that provider. At least four routes are not variables. **A well-known key file**, `/home/claude/.claude/remote/.api_key`: the CLI reads an API key from it whenever `CLAUDE_CODE_API_KEY_FILE_DESCRIPTOR` is unset, with nothing gating the read, and bills it (read from source). It exists on Claude Code's own remote hosts, whose user is `claude`; construction refuses `auth = "subscription"` when it exists, since the check is deterministic and cheap. Its sibling `.oauth_token` is a subscription token and is left alone, as `CLAUDE_CODE_OAUTH_TOKEN` is. **The `ant` CLI's profile store**, at `$XDG_CONFIG_HOME/anthropic`, or `~/.config/anthropic` when that is unset: the CLI can use a profile there in place of the login, but that precedence is read from source and not measured, and refusing on the store's mere existence would block operators who use the `ant` CLI for other things — so it is not refused, and it stays on the live-validation checklist. **An `apiKeyHelper` in user settings**, which loads only if a host opts into `"user"`. **An `apiKeyHelper` in managed settings**, which always load (§3.5.3): that is the machine administrator's policy, above BOS. The default loading no user, project or local settings file closes the repository's own `apiKeyHelper` (§3.5.3). The check reads `os.environ` and the key file as they stand at construction; anything set afterwards is not seen. Claude Code has no counterpart to Codex's login preflight, so an absent login is not detected before the first turn. `auth = "api_key"` is the explicit opt-in that suppresses the check. BOS never stores a token.

#### 3.10.4 Packaging

Two independent extras, out of `all` (the Claude wheel alone is 97 MB on linux x86_64), in the dev group so pyright checks the runtimes against real SDK types and a fake-backed suite can be written against real shapes:

```toml
claude-code = ["claude-agent-sdk==0.2.159", "mcp>=2.0,<3", "bos-ai[gateway]"]
codex       = ["openai-codex==0.156.1",     "mcp>=2.0,<3", "bos-ai[gateway]"]
```

`mcp` is pinned to 2.x explicitly. `claude-agent-sdk` allows `>=1.23,<3`, and the two majors are not compatible: 1.x's `FastMCP` became `mcp.server.mcpserver.MCPServer` in 2.x, and `mcp/server/fastmcp.py` in 2.x exists only to raise `ModuleNotFoundError` with a migration hint. `claude-agent-sdk` itself imports only `mcp.server.Server`, `mcp.types` and `mcp.shared.*`, all of which 2.x still exports. `bos-ai[gateway]` supplies starlette and uvicorn for §3.8.

A missing extra surfaces as an actionable error at `create_agent` naming the extra to install — not an `ImportError` traceback at first turn.

| Pair | Distinction |

| `mcp_tools` vs `tools` | `tools` is BOS's own include list and is dropped for external runtimes (§3.9). `mcp_tools` is the MCP egress allowlist. Different mechanisms, no overlap. |
| A reserved kind vs an agent that inherits it | `codex` is the runtime's name and the zero-config agent. `george` (`_parent: codex`) is a named instance with its own prompt, `cwd` and permission; `AgentPort.name` reports `george`. §3.4. |
| `system_prompt` vs `base_instructions` | Both are "the prompt". On an external runtime `system_prompt` is *appended* to the harness's own and `base_instructions` *replaces* it. On a BOS `Agent` there is no harness prompt, so `system_prompt` is the whole thing — the same key, the same intent, a different base. §3.4.1. |
| BOS `system_prompt` vs `CLAUDE.md` / `AGENTS.md` | `system_prompt` is per-agent config BOS sends over the wire. The project docs are files under `cwd`, written by the repository: codex reads `AGENTS.md` itself, and for Claude Code BOS reads the root `CLAUDE.md` and sends it after `system_prompt`, unless the CLI loads it itself under `"project"` (§3.4.1.4). Three layers, §3.4.1. |
| Codex `Sandbox` vs Claude `SandboxSettings` | An OS filesystem sandbox vs bash-command isolation only. §3.5. |
| `permission` vs Claude Code's `permission_mode` | `permission` is BOS's three-value enum, the key a config author writes. `permission_mode` is the vendor's approval policy, which BOS derives from it and never takes from config — a `native_options` naming it is refused. §3.5. |
| Claude Code's `PreToolUse` hook vs `can_use_tool` | Both are BOS callbacks the CLI consults about a tool call. The hook fires on every call in every mode and its deny holds against allow rules and `bypassPermissions` (measured on `Write`): it is the file-tool confinement. `can_use_tool` is asked only where the CLI would otherwise prompt, which a mode or an allow rule can pre-empt: it is the answer to a prompt, never a gate. §3.5.3. |

### 3.12 Hosts that hold several workspaces

BOS is a library. The first host embeds it and may manage several workspaces inside one application, so "per process" and "per workspace" are not interchangeable here, and this section states which is which for everything BEP 19 adds.

**Everything BEP 19 adds is per harness, and a harness is per workspace.** The two runtime objects are built by `create_agent` and tracked in that harness's `_owned`; each `CodexAgent` owns its own `codex app-server` child; each `ClaudeCodeAgent` spawns and disconnects its CLI child within one turn; the MCP server (§3.8) is one per harness, on an **ephemeral** loopback port — never a fixed one — with a bearer token per agent. Two workspaces in one process therefore get two MCP servers on two ports with disjoint tokens, and closing one harness touches nothing the other owns.

**Three things are process- or user-global, and the design has to live with each:**

1. **`ep_tool` is a process-global registry.** The MCP egress reads it by name (§3.8), so two workspaces in one process draw from one pool of tool names. The `mcp_tools` allowlist is per agent and is what scopes exposure, but it cannot disambiguate two workspaces' extensions registering different implementations under one name — `ExtensionPoint.register` logs a warning and the last writer wins ([`registry.py:67-70`](../../src/bos/core/registry.py)). That is BEP 4's property, not something BEP 19 changes; a host wanting per-workspace tool implementations must either namespace the names or keep the workspaces in separate processes.
2. **Native session storage is per OS user, not per workspace.** Claude Code writes transcripts under `~/.claude/projects/`; Codex keeps threads under `CODEX_HOME` (default `~/.codex`). Reads are safe because BOS always addresses a session by the explicit id it stored (§3.6) and passes the resolved `cwd` as `directory` to `get_session_messages`, so lookups are scoped and ids do not collide across workspaces. What is *not* isolated is the storage itself: one workspace's operator-visible transcript directory is every workspace's. Relocating Codex's would mean moving `CODEX_HOME`, which also holds `auth.json` and would break subscription login (§8.2).
3. **The environment.** Neither runtime gives its child an environment of its own. Each SDK starts from the whole of BOS's `os.environ` and layers the per-client `env` over it — `claude-agent-sdk` drops only `CLAUDECODE` first (`subprocess_cli.py:815-821`), `openai-codex` nothing (`client.py:258-260`) — so `ClaudeAgentOptions.env` and `CodexConfig.env` can override a variable but never remove one, and each child inherits whatever is in the process environment, including what a workspace's `[platform.envs]` wrote there. This item used to say each runtime "passes an explicit environment to its child rather than letting it inherit"; neither does, and §3.8 already said as much of `CodexConfig(env=…)`. What a runtime can do is override, and the principle for Claude Code is this: **the inherited environment is trusted operator configuration** — the SDK cannot unset it, and it is set by the person who runs BOS — **except for variables that load what BOS's default leaves out (§3.5.3), which `ClaudeCodeAgent` overrides in every client's `env`** with the value that switches each off. The list is enumerated from the CLI 2.1.281 source, the version `test_what_was_read_from_the_cli_source_is_pinned_to_its_version` pins: the variables the CLI reads whose names put them on its plugin, hook, settings, MCP, skill or agent loading paths, each then read where it is used. Each value is checked against that variable's parser in the source, because an override switches a variable off only if the CLI reads the value as off: `M.bool` counts a value as set only when it is `1`, `true`, `yes` or `on`; `M.triBool` reads `0`, `false`, `no` and `off` as an explicit false; `M.str` reads an empty value as unset. A variable the CLI read as set by its mere presence could not be switched off this way — the SDK cannot unset — and BOS would refuse to start while it is set; none on the list is. The method has a limit worth stating — a loader whose variable is named for none of those paths would be missed; two were, until followed from a runner message and from a reviewer's measurement, and are recorded below. **The pre-existing blocker, named rather than solved.** A host cannot hold two workspaces open *concurrently* today, and BEP 19 does not change that. `BosApp.__aenter__` refuses a second live instance in one process, and its own comment gives the reason: `bootstrap_platform()` writes `os.environ` and rebuilds the agent registry, so two would overwrite each other ([`sdk/_app.py:20-27`, `:51-58`](../../src/bos/sdk/_app.py)). `open_harness` has the same hazard, because it calls the same `bootstrap` ([`sdk/_bootstrap.py:14-32`](../../src/bos/sdk/_bootstrap.py)), and the shared state is `AgentRegistry`'s class-level dict, the `[exts]` defaults merged into process-global `ExtensionPoint` objects, and `[platform.envs]`. Sequential use — open, use, close, open the next — works today and is what §4.1 shows.

Making concurrent multi-workspace hosting work means moving that state off the process, which is a BEP 18 / BEP 6 change with its own fallout and is out of scope here. What BEP 19 owes it is not to deepen the hole: every criterion in §7 that could be affected is asserted per harness, and §7.27 pins that two harnesses opened in sequence leave no shared runtime state behind.

## 4. Audience flows (end state)

### 4.1 Embedder

```python
async with BosApp(config, bos_dir=".bos") as app:
    coder = await app.build_agent("codex", agent_cfg={
        "cwd": "services/api", "permission": "workspace-write",
        "mcp_tools": ["DeskCreateTask"], "timeout_seconds": 1200,
    })
    reply = await coder.ask(chat_id, "Add a health endpoint and run the tests.")
    for message in await app.get_messages(chat_id):   # full native transcript
        render(message)
```

The same `chat_id` on the next call resumes the same Codex thread. `app.agent("george")` works without `build_agent` when the workspace ships an `agents/george.md` with `_parent: codex` (§3.4) — which is the shape most projects should use, since the agent then has its own name and its own prompt file.

A host holding several workspaces opens them **one at a time** (§3.12) and picks the prompt route that matches where its prompts live — the workspace's own `agents/george.md` when the prompt belongs to the project, or `agent_cfg` on a bare reserved kind when the host keeps prompts per tenant instead of shipping a named agent file (§3.4.1.1 — `george` would already be cached by `__aenter__` the moment a workspace ships that file):

```python
for ws in tenant_workspaces:                       # sequential: BosApp is one-per-process
    async with BosApp(ws) as app:
        coder = await app.build_agent("codex", agent_cfg={
            "permission": "read-only",
            "system_prompt": prompts.for_tenant(ws.name),   # a resolved string, never a path
        })
        await coder.ask(chat_id_for(ws), task)
```

### 4.2 End user

Through a BOS agent, unchanged: the main agent calls `AskSubagent(role="coder", task=…)` and the external runtime executes, because `AgentRunner` resolves a role to an agent kind (§1.2). Directly: `boscli ask --agent codex "…"`.

### 4.3 Operator

- `boscli inspect agent codex` reports the resolved runtime, the absolute `cwd`, the `permission` level, and the resolved `mcp_tools` with any unmatched names (§3.3.1). It reports neither the extra nor the login: a missing extra raises before there is an agent to report on, and the login is only checked on the first turn, which `inspect` does not run.
- A missing extra, an escaping `cwd`, an unknown config key, a `native_options` naming a setting the runtime sets itself — for Claude Code, any setting outside its allowlist, a misspelt one included, each with its reason (§3.4) — and two Claude Code refusals — `workspace-write` on Windows or where the bash sandbox's dependencies are missing, naming what to install (§3.5.3), and `auth = "subscription"` with any variable in the environment that stops the CLI using the subscription login, or with the CLI's well-known key file present (§3.10.3) — all fail at `create_agent` with a message naming the fix. A Claude Code agent whose `setting_sources` includes `"project"` or `"local"` builds, and logs one WARNING that the repository's settings then run commands on the host outside the sandbox and outside `permission` (§3.5.3). A Claude Code agent's root `CLAUDE.md` that is not a regular file inside its `cwd` — a symlink out of it, say — is left unread, and one over 40,000 bytes is cut short; either logs a WARNING that names the file, once per agent for each problem, at the first turn that meets it rather than at build (§3.4.1.4). An operator who wants no repository text in a Claude Code agent's prompt sets `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`, the CLI's own switch, which BOS's read obeys (§3.4.1.4). **An absent login does not**, on either runtime: Codex's `auth` preflight is an RPC and runs on the first turn, so `create_agent` succeeds and the first `ask()` raises; Claude Code has no login check at all (§3.10.3).
- Unmatched `mcp_tools` names appear as warnings, once, at build.
- Native transcripts are where the runtime puts them; `app.get_messages(chat_id, source="bos")` is the record BOS guarantees (§3.7).

### 4.4 Background / automated

An external agent bound to an actor runs under the gateway like any other: turn admission, interrupt, event fan-out and shutdown drain all work through `AgentPort`. Shutdown calls `request_stop()`, which interrupts the native turn; `aclose()` reaps the child. Nothing waits on an approval (§3.5.4), so an unattended run cannot hang on one.

## 5. Compatibility and fallout

### 5.1 Breaking: four signatures widen from `Agent` to `AgentPort`

`create_agent`, `BosApp.agent`, `BosApp.build_agent`, `AgentActor.__init__`. At runtime nothing changes — `Agent` satisfies the protocol. For an embedder type-checking against `bos.sdk`, a call to an `Agent` member outside `AgentPort` on the *result* of these now fails. No such member is called anywhere in this repo (§3.3).

`bos.sdk.__all__` grows by **five** names, not one: `AgentPort`, plus `MessageContent`, `TextPart`, `ImagePart`, `FilePart` (34 → 39). Only three of the four content names are forced. `AgentPort.ask`/`AgentPort.run` annotate `content` as `MessageContent`, a bare `TypeAlias` (`str | list[MessageContentPart]`); `test_promised_ports_are_implementable_from_the_contract_alone` calls `typing.get_type_hints()` on every promised Protocol's methods, and `get_type_hints` inlines a plain `TypeAlias` at the call site — so the test never sees the name `"MessageContent"` at all, only the `TextPart` / `ImagePart` / `FilePart` TypedDicts the alias expands to, and only those three are what the test actually requires `__all__` to contain. `MessageContent` itself is promised by hand, alongside them: an implementer building a non-string `content` value from the contract alone needs the alias's own name, and promising the leaves but not the union the signature is written in terms of would be an odd contract to hand someone. (`bos.sdk/__init__.py`'s own comment on the `FilePart, ImagePart, TextPart` import spells out this same distinction — an earlier version of that comment claimed the test forced all four, which was corrected once the mechanism above was traced through `typing.get_type_hints`.) BEP 18 §3.8's contract list now carries all five new names (BEP 18 §9, 2026-09-24), and both `test_the_contract_surface_is_importable_and_identical` and `test_promised_ports_are_implementable_from_the_contract_alone` pass with `AgentPort` in `__all__`.

### 5.2 Breaking: `[agent.defaults]` no longer reaches the two reserved kinds

Only observable in a project that both sets `[agent.defaults]` and uses a reserved kind — impossible before this BEP, since the kinds do not exist. Recorded because the registration loop's uniformity is what changes (§3.2.1).

### 5.3 Not breaking

`Agent` is unmodified. `ChatStore` is unmodified (§3.7). `ep_tool`, `ep_agent`, `SubagentPlugin` and the plugin lifecycle are unmodified. `boscli inspect` gains a branch; its output for a BOS agent is unchanged. `BosApp.build_agent`'s new parameter is optional. A base install with no extras imports `bos.sdk` and builds BOS agents exactly as before.

### 5.4 Third-party impact

Two new optional dependencies, each pinned exactly, each carrying a vendor CLI binary. Both vendors ship these SDKs under their own release cadence and Codex's app-server protocol is marked experimental upstream — hence exact pins and a §7 criterion that the pinned versions are the ones tested. An extension that subclasses `Agent` is unaffected. An extension that type-annotates against `create_agent`'s return type must widen with it.

**Satisfiable without a vendor SDK or network (Layers 1–3):**

1. `create_agent("codex")` with no `permission` key raises at construction, and the message names the key and its three values.
2. `cwd = "../outside"` raises at construction, naming the resolved path and the workspace.
3. An unknown key under `[agents.codex]` raises, naming the key.
4. `[agent.defaults] model = "x"` plus `[agents.codex]` yields a `CodexAgent` whose resolved native model is not `"x"`.
5. `mcp_tools = ["NoSuchTool"]` logs exactly one warning naming the agent and the tool, and starts no MCP server.
6. An in-process MCP client with agent A's bearer token lists and calls only A's subset; agent B's token cannot reach A's tools; a request with no token is rejected.
7. `harness.__aexit__` leaves no live MCP server and no child process.
8. `tests/test_sdk.py::test_the_contract_surface_is_importable_and_identical` and `::test_promised_ports_are_implementable_from_the_contract_alone` pass with `AgentPort` in `__all__`.
9. `boscli inspect agent <external>` succeeds and reports runtime, absolute `cwd`, `permission`, resolved `mcp_tools`, and any of those names the host has no `ep_tool` for — in text mode, which is the default, not only under `--json`. Read from the runtime's `resolved_config` (§3.3.1), so it holds on an agent that has never run a turn.
10. `import bos.sdk` on a base install with no extras succeeds; `create_agent("codex")` there raises an error naming `bos-ai[codex]`.
11. An `agents/george.md` whose frontmatter is `_parent: codex` and whose body is a prompt builds a Codex-backed agent whose `name` is `george` and whose `system_prompt` is the file body. `[agents.codex] cwd = "x"` reaches `george` unless `george` overrides it. A workspace naming neither reserved kind has no `codex` entry in `AgentRegistry.describe()`, and `resolve_default_agent()` is unaffected.
12. A hand-written `external_runtime` key raises, and the message names `_parent` (§3.4). Setting both `system_prompt` and `base_instructions` raises (§3.4.1).
13. With no `CLAUDE.md` in `cwd`: with `system_prompt` set, the Claude Code command carries `--append-system-prompt` and **not** `--system-prompt`; with neither prompt key set, it carries **neither** flag; with `base_instructions` set, it carries `--system-prompt <text>`. With a root `CLAUDE.md`, `"project"` not in `setting_sources` and `CLAUDE_CODE_DISABLE_CLAUDE_MDS` not set: `--append-system-prompt` carries the file after `system_prompt`, under its heading — so the neither-set case carries that flag too — `base_instructions` still carries only its own text, and a `CLAUDE.md` that is not a regular file inside `cwd` adds nothing (§3.4.1.4). Asserted on the built command, not on the resolved config, because the defaulting trap in §3.4.1.3 is invisible at the config layer.
14. `uv run pytest -q`, `uv run ruff check src tests examples`, and `npx -y pyright src` are green, pyright at zero errors.

**Requires a real subscription login (Layer 4–5, per runtime, recorded in §8.1):**

15. A turn starts, streams `TurnEvent`s that a host renders, and returns an `AgentResult` with non-empty `usage`.
16. A second `ask()` on the same `chat_id` continues the same native session — asserted by the native session/thread id, not by the model's reply.
17. After a BOS process restart, a third `ask()` on that `chat_id` resumes it, recovered from `ChatStore` metadata alone.
18. Under `permission = "workspace-write"`, a write inside `cwd` succeeds and a write outside it **fails** — observed, per §3.5.5. Under `read-only`, every write fails. For Claude Code this is now asserted in CI against the real CLI with the fake model (`tests/test_claude_code_confinement.py`), per level and per mechanism: `read-only` writes nothing (in-root or out) and reads only inside the root (an out-of-root `Read` fails); `workspace-write` confines both file-tool writes (the hook) and bash writes (the sandbox) to `cwd`, each out-of-root escape spelling denied (`..`, an in-root symlink pointing out, an absolute path, a relative path); `full-access` writes out-of-root, confining nothing on the filesystem; the cross-session and interactive tools are neither offered nor callable at any level; the CLI's config directory is denied; and — the case `can_use_tool` cannot hold — a workspace the operator has trusted whose own `.claude/settings.json` allows `Write` (an agent with `setting_sources` including `"project"`): a write outside `cwd` still **fails**, denied by the hook where the repo's allow rule approved it (fact 4). Under the default, none of a repository's hooks, `apiKeyHelper` or `.mcp.json` server runs, at any level (§3.5.3). Nothing else about reads is asserted, for either runtime, because nothing else bounds them (§3.5.5): a bash read and an `@path` read outside `cwd` are unconfined and documented as such (§8.2). And when a Codex agent asks to escalate past the sandbox, the request is **refused by Codex, the agent continues the turn**, and **no approvals reviewer is consulted** — the refusal arrives as Codex's own "you cannot ask for escalated permissions if the approval policy is Never", not as a BOS WARNING, because under `never` no request reaches `_deny_approval` (§3.5.4). CI now proves this against the real child with a fake model; the live run confirms it under a real model that might phrase the request differently. §3.5.4's refusal *values* are no longer exercised by any expected path — they answer only a request Codex was not supposed to send.
19. `request_stop()` mid-turn interrupts the native turn, which stops writing to the workspace, and the turn returns what it had produced with its runtime's `finish_reason` for an interrupted turn: `"interrupted"` for Codex; for Claude Code the CLI's own `terminal_reason`, `"aborted_tools"` while a tool ran or `"aborted_streaming"` while the model answered (§3.9). Preconditions: the child confirms the interrupt within the grace — one that does not is abandoned (§3.10.2) and keeps writing until the client closes. For Codex, reaping the child is `aclose()`'s job, not `request_stop()`'s; `request_stop()` only sets the flag each in-flight turn races. A Claude Code turn closes its own client, and with it its CLI, when it ends — CI asserts against the real CLI that nothing is left running in `cwd` after a stopped turn returns. A turn started *after* it is not raced at all — it returns the shutdown marker before any vendor call, so no thread is opened and no billable turn is started, which is what `Agent` does by checking the flag at the top of its first iteration.
20. `timeout_seconds` expiry raises. Precondition: it bounds one turn *attempt*, not the whole call — each schema retry gets a fresh window. Expiry while the turn is streaming interrupts the native turn first. Expiry during setup interrupts nothing and says which phase it was: for Claude Code's `connect()` and Codex's `thread_start`/`thread_resume` nothing had started, but for Codex's turn request the child may have started the turn anyway and BOS has no id with which to stop it — the §8.2 orphan limitation, observable only on a live server (§6 step 13).
21. `schema=` returns validated structured output through each runtime's native mechanism.
22. With `mcp_tools` set, the runtime lists and successfully calls the exposed BOS tool, and an unexposed `ep_tool` is not callable.
23. `app.get_messages(chat_id)` returns the native transcript — the user and assistant messages in the runtime's own session, in order, including ones BOS never authored — while `source="bos"` returns the two-message-per-turn record. Three preconditions, all of them §3.7's rules and all of them things a tester running this against a live server will otherwise read as a mismatch: (a) *messages*, not tool activity — projecting it would mean forging the `tool_calls`/`tool_call_id` pairing BOS uses and Codex does not have, and an earlier draft of this criterion said "including tool activity" and was wrong about what a `Message` can carry; (b) Codex `commentary`-phase agent messages are **dropped**, so a turn the `codex` CLI renders with visible commentary yields fewer assistant messages here than the CLI shows; (c) a turn the runtime reports as not fully loaded appears as one gap marker rather than as missing messages.
24. Quota exhaustion and an expired login each surface as a distinct error; neither falls back to API-key billing.
25. With `system_prompt` set, the runtime's reply reflects it while its own tool guidance still works — the pairing §3.4.1 protects. `native_options` reaches the child: a keyword (`personality`) and a config key (`config.project_doc_max_bytes`) are both accepted by `thread_start`, and the turn completes. Observed in live runs 2 and 3, and the config half asserted in CI by `test_native_options_config_merges_rather_than_replacing`. This criterion used to add that `project_doc_max_bytes = 0` stops the reply reflecting an `AGENTS.md` placed in `cwd`; runs 2 and 3 disproved that — the reply reflected it both times — so the claim is removed rather than kept as a failing criterion (§3.4.1.4). The `system_prompt` half was not exercised by any live run and is unverified.
26. Criteria 15–25 hold at the pinned SDK versions, and those versions are what CI installs.

**Multi-workspace (§3.12), satisfiable with fakes:**

27. Two harnesses opened and closed **in sequence** over different workspaces each get their own MCP server on a different ephemeral port with disjoint bearer tokens, and after the second closes no port is listening, no child process survives, and nothing BEP 19 added remains in process-global state.

### 8.2 Unresolved

- **Whether `full-access` should exist at all.** Kept because a trusted local dev loop is a real use case, but it is the one level where BOS enforces nothing. Candidate for requiring an explicit second opt-in.
- **Where process-global BOS state should live so a host can hold several workspaces at once.** `AgentRegistry`'s class dict, the `[exts]` defaults merged into `ExtensionPoint` objects, and `[platform.envs]` writing `os.environ` are the three (§3.12). A BEP 18 / BEP 6 question, listed here because the first host wants it and because BEP 19's §7.27 is the guard that this BEP does not add a fourth.
- **Claude Code `session_store`.** Would make transcripts workspace-local and portable (§3.7). Deferred; the argument for doing it is that `~/.claude/projects/` is the wrong home for a server's data.
- **An orphaned Codex turn, after a `thread.turn` timeout.** `timeout_seconds` bounds the turn request (§3.10.2), but cancelling it does not stop the work: `AsyncCodexClient._start_turn` submits to a module-level executor and awaits it through `asyncio.wrap_future`, and its cancel path only closes the orphaned *subscription* — the vendor's own docstring calls this "releasing an unclaimed result". The native turn therefore starts, and BOS cannot interrupt it, because `turn_interrupt` takes a turn id and the turn id is precisely what the cancelled call never returned. The turn ends when `aclose()` closes the client. Not a regression: before the bound the call hung *and* the turn ran — bounding it traded a silent hang for a silent orphan. No fix now, deliberately: recovery would mean reading the thread back to find an in-flight turn and building a handle for it, speculative work on a rare path over an RPC that can wedge the same way. Revisit if the vendor exposes the started turn id on the cancel path, or if the orphan is observed. **Observed so far: none.** In all three live runs no orphaned turn was seen: after a `thread.turn` setup timeout (`timeout_seconds = 2`) the file the prompt asked for did not appear within a 60s window. In runs 2 and 3 the timeout raised at 2.8s and 3.0s and `aclose()` then returned at once. That does not disprove the limitation — it is reasoned from the vendor's cancel path, and a 60s window over three runs is a small sample — so the entry stays, with this as the evidence against it being common.
- **Nothing pins the *set* of Codex approval methods.** `_APPROVAL_DENIALS` (§3.5.4) is keyed by the five approval methods in today's `ServerRequest`; a sixth added by a future `openai-codex` would fall through to the `{}` the other five server requests get. Deliberately not guarded, because the failure is loud rather than silent: `{}` fails `required` on every approval response shape in the schema, so the server sees a malformed response — not the auto-accept this handler exists to kill. A test *could* pin the set by regenerating the schema from the shipped binary and diffing the method list, which is why this is a watch item and not an impossibility; it was judged not worth a subprocess in CI for a failure mode that announces itself. Re-generate (`codex app-server generate-json-schema`) and diff when the `openai-codex` pin moves.
- **`get_messages(source="native")` cannot tell two agents on one runtime apart.** `commit_external_turn` records the *runtime* per turn (§3.6), not the agent kind, so when two built agents both declare `external_runtime = "codex"` — a bare `codex` and a `_parent`-inheriting `george`, say — nothing in the store says which served the chat. They are not interchangeable in general either: a Claude Code transcript is keyed by the agent's `cwd`, so the wrong one reads a different conversation. `BosApp.get_messages` therefore raises, naming both kinds and pointing at `app.agent(<kind>).native_messages(chat_id)`, rather than picking one. Revisit by adding the agent kind to the metadata `commit_external_turn` writes; deferred because that widens a stored schema every external turn already writes, for a case the first host does not have.
- **A Codex turn whose `items_view` is not `full` has no recovery path.** §3.7 makes it a visible gap marker, which is the honest answer but not the useful one: the messages genuinely are not in the `thread/read` response. The vendor does expose `thread/items/list` (`ThreadItemsListParams` takes `threadId`, an optional `turnId`, a cursor and a limit), which looks like the paged read that would materialize them, but `AsyncCodex` wraps no such method and `AsyncThread` has none — reaching it would mean a raw JSON-RPC call past the SDK's public surface. Revisit if `openai-codex` wraps `thread/items/list`, or if a real long-lived thread shows the markers are common enough to be worth the reach-past.
- **Nothing pins the *set* of `TurnItemsView` values either, and here the failure is total rather than per-turn.** §3.7's gap marker handles `notLoaded` and `summary`, and the check is written as "not one of the loaded values" so an unknown value would be treated as not-loaded — but it never gets there. `TurnItemsView` is a closed `Enum`, so a value a future `openai-codex` adds fails `ThreadReadResponse` validation inside the vendor's own `thread_read`, and `native_messages` surfaces that as "the native transcript … could not be read". There is no per-turn degrade to reach for: the response never parses, so the whole read dies, not one turn of it. Same family as the approval-method entry above and the same revisit condition — when the `openai-codex` pin moves, regenerate the schema (`codex app-server generate-json-schema`) and diff the enum.
- **The Codex MCP wiring is proven end to end — `tools/list` in CI, calling live.** §3.8's Codex half is `thread_start`/`thread_resume`'s `config={"mcp_servers": {"bos-tools": {"url": …, "bearer_token_env_var": …}}}` plus `CodexConfig(env={<that var>: <token>})`. This is no longer inference: `tests/test_codex_mcp_wiring.py::test_the_real_codex_child_reads_the_override_and_lists_the_tool` spawns the **real** `codex app-server` — no login needed for `thread_start` — and asserts that the child reads the override, connects to BOS's loopback server, authenticates with BOS's token and lists exactly the granted tool. The `config=` and `-c` channels are the same one, also measured: a `bearer_token` planted through either is refused with the same inner sentence, `bearer_token is not supported for streamable_http`. Only that sentence matches — each channel wraps it differently (`failed to load configuration:` over JSON-RPC, `failed to load bootstrap configuration` / `Caused by:` from the CLI), so it is the diagnosis that is shared, not the whole string. §7.22 has three clauses — the runtime lists the tool, calls it, and cannot call an unexposed one — and this proves the first. The third is proven, but at BOS's own server rather than through the child (`test_mcp_egress.py::test_a_tool_outside_the_allowlist_is_refused_without_executing`). The second and the third seen from the child's side needed a model turn and so a login, and live runs 2 and 3 observed both: Codex called the exposed BOS tool and the host implementation ran, and a registered `ep_tool` outside `mcp_tools` was not reached (§8.1, §7.22). Run 3's call went through BOS's pre-approval rather than a reviewer (§3.5.4). `CodexConfig(config_overrides=…)`, the `--config` passthrough, is no longer a fallback worth holding: it was there in case `config=` turned out not to be the channel, and it is; it would also put the bearer token on the child's command line for any local `ps`.
- **BOS's `[mcp_servers.bos-tools]` entry shares a namespace with the operator's own; the loud half of that is unresolved and the quiet half is closed.** `config=` *merges* rather than replaces, per key even for a whole-table override — overriding the table wholesale with a complete entry still left a `bearer_token_env_var` from `config.toml` in place. **Loud, unresolved — two of them, both total:** if the operator's same-named entry is **stdio**, the whole config stops loading ("url is not supported for stdio in `mcp_servers.bos-tools`"); if it is HTTP and carries `bearer_token`, that key is rejected for streamable HTTP wherever it comes from and the operator's copy is merged in beside ours, so the config stops loading too. Either way every turn fails, and at least the error names the table. **Live, and a different kind of neighbour:** a colliding entry carrying `http_headers_helper` makes Codex **execute a command** — measured, the operator's helper ran and wrote its marker file — even though the header it printed lost to BOS's. Sharing this namespace is therefore not only about which credential wins; it can also run code the operator configured for a different server. Mitigated only by the name — `_MCP_SERVER_NAME` is `bos-tools`, what the server already reports for itself over MCP, and less likely to be a table someone already wrote than `bos`. Not resolved further because the remaining fixes are worse: a random name is unreadable in the operator's own config, and `CODEX_HOME` cannot be relocated, for the reason below. **Quiet, now closed:** an earlier round shipped `http_headers`, and against an operator entry carrying `bearer_token_env_var` the child sent *theirs* — measured, not conditional. A 401 from `_gate` does not fail `thread_start`, and `_gate` logs no refusal while the server runs with `access_log=False`, so the agent would simply have had no BOS tools and nothing would have said so. BOS now sends `bearer_token_env_var` itself, which wins against each of the four credential keys the binary's own `codex mcp get --json` enumerates for a streamable-HTTP entry (§3.8), so this path no longer produces a silent toolless agent. The OAuth path named there is unmeasured and is the one shape that could still reopen it. `_gate`'s silence is still worth fixing on its own account — revisit by logging the refusal there, deferred because an unauthenticated endpoint that logs on every probe is its own problem.
- **`native_options`' reserved list is a denylist, and nothing proves it complete.** §3.4 rejects a `native_options` naming any setting the runtime sends as a typed parameter, plus `config.mcp_servers` and `config.sandbox_workspace_write`. The first group is closed as far as anything here is: it is derived from `_BOS_THREAD_KWARGS`, which a test pins to the keywords actually sent — for keywords sent *unconditionally*, which is all of them today and is the pin's own stated limit. The second group is not closed at all. `sandbox_workspace_write` was found by probing candidates against the `SandboxPolicy` the server resolves — seven candidate settings probed, one moved it — and probing is not enumerating. There is no listing of Codex's config surface BOS can read: no `codex mcp get --json` equivalent for top-level config, and the app-server schema models `ThreadStartParams.config` as an untyped object. Two axes the probe could not see at all, both real: settings that change what the child's *shell* inherits (`shell_environment_policy`) rather than what the sandbox permits — which also decides whether the agent can read BOS's own MCP bearer token out of its environment — and live runs 2 and 3 observed that it can see it (§3.8) — and settings that grant reach through a *tool* rather than the sandbox. Neither is reserved, because neither was shown to move anything and reserving on a guess blocks a legitimate knob. **A guard that is inert and a guard that works look identical until someone measures, and this entry has one of each in its history.** The reservation first matched only the literal key, so Codex's own dotted spelling (`sandbox_workspace_write.writable_roots`, the syntax `codex --help` documents for the same channel) walked straight past it and the measured widening was still reachable. The same hole was open on `config.mcp_servers`, and there the credential **was** reachable, about half the time. Codex applies each key of `config` as an independent override at its own dotted path, in an order it does not fix — the same map sent twice to the same child resolves differently — and each application replaces the subtree at the path it names. A nested table and a dotted path under the same head are therefore a race, not a precedence: with a nested table and *k* dotted sub-keys under one head, all *k* survive about `1/(k+1)` of the time (measured 0.55 / 0.30 / 0.33 / 0.20 for k = 1..4, n = 60; the mechanism reproduced independently at n = 30 on `sandbox_workspace_write`, 11 wide to 19 narrow against a predicted 1/3 for k = 2). It is not per-table — the same coin flip appears on `mcp_servers`, `tools` and `shell_environment_policy` — and nothing is unioned. Measured against BOS's own shape, a host `mcp_servers.bos-tools.command` landed on top of BOS's entry in 36/60 and 25/60 runs: BOS's nested table did not shadow the host's dotted key, it won a coin flip. One rule now refuses both spellings on both tables, which closes it. The typed parameters are unaffected — they beat `config` every time (40/40 each for `sandbox_mode`, `approval_policy`, `cwd`, `model`) because they are not config overrides at all.
  **Two lessons, and the branch paid for both.** An explanation of *why* something is safe is itself a claim that needs measuring: this entry carried a borrowed one, then a home-grown one, and the data refuted each in turn. And a measurement of a nondeterministic system is not a rule until it is repeated — three observations of a coin flip is what produced the second wrong explanation, which read as "narrower wins" and was a small sample.
  **The stance this rests on:** `native_options` is trusted config, written by the same person who writes `permission`, so an incomplete denylist is a missing guard-rail and not an escalation path — nothing the *model* produces reaches it. That is a persistence path implied by granting write access to the directory the config lives in, not something this design adds, and it is the same door as editing `agents/*.md`. ### 8.3 Resolved during design

- **Whether to subclass `Agent`** — no. §3.3.
- **Whether a `runtime = …` agent key selects the runtime** — no; the kind's name does, and `runtime` / `harness` would collide with existing top-level sections. §3.2, §3.11.
- **Whether to expose each runtime as start/continue/poll/cancel delegation tools instead of as an agent** — no. §1.2.
- **Whether `mcp_exportable` belongs on `@ep_tool`** — no; the `mcp_tools` list is the single gate. §3.8.
- **Whether `_parent = "codex"` should work** — yes, and it is the recommended shape. Reversed twice during design: first blocked to keep dispatch keyed purely on the name, then restored once the `.md` authoring route (§3.4.1.1) made named instances the natural home for a prompt. Dispatch is now "the reserved name, or the `external_runtime` inherited from it", which costs one dict merged into an existing resolver call. §3.2, §3.4.
- **Whether `system_prompt` should carry over to external runtimes** — yes, meaning *append*, with `base_instructions` as the explicit replace. An earlier draft renamed it to `instructions` and rejected `system_prompt`; that would have broken the `.md` route, where the body lands in `system_prompt` and no one writes the key by hand. §3.4.1.
- **Whether the prompt should be a path-valued config key** — no. Paths resolve against something, and in a multi-workspace host that something is ambiguous. Files are read by `resolve_agents()`, which knows the workspace root; everything below sees a resolved string. §3.4.1.1, §3.12.
- **Whether `chat_id` should encode the runtime** — no; stored metadata already carries it. §3.7.
- **Whether `ChatStore.get_messages` should transparently return native transcripts** — no; the read is additive on `BosApp`. §3.7.
- **Whether to use Claude's in-process SDK MCP server** — no; one HTTP server serves both runtimes with one implementation. §3.8.
- **Whether to serialize sandboxed turns of agents that share a `cwd`** — no. Their race on the sandbox's mount points is documented and accepted: it is rare and fail-closed, two writers in one directory race on the files anyway, and a per-`cwd` lock would change BOS's concurrency semantics. §3.5.3.
- **Whether BOS's read of `CLAUDE.md` obeys the CLI's switches for memory files** — yes, all three its memory gate obeys (`CLAUDE_CODE_DISABLE_CLAUDE_MDS`, safe mode, bare mode), by the CLI's own rule for each, since the read stands in for the CLI's memory loading; the first is also the opt-out, with no BOS key of its own. §3.4.1.4.

  Four passages proved wrong and are corrected in place rather than footnoted. **§5.1** claimed `bos.sdk.__all__` grows by one name (`AgentPort`); it grew by five, 34 → 39 (`AgentPort`, `MessageContent`, `TextPart`, `ImagePart`, `FilePart`), and only three of the four content names are compelled by `test_promised_ports_are_implementable_from_the_contract_alone` — `AgentPort.ask`/`run` annotate `content` as the bare `TypeAlias` `MessageContent`, which `typing.get_type_hints()` inlines to its member TypedDicts before the test ever sees the alias's own name; `MessageContent` is promised by hand, and `bos/sdk/__init__.py`'s own comment on the point now says so. **§3.2**'s code sketch showed `EXTERNAL_AGENT_KINDS: dict[str, type]` mapping kinds straight to the runtime classes, and `merged_cfg.pop("external_runtime", None)`. Neither survived contact with the rest of the repo: `bos/core/harness.py` sits on the import path of a base install with no extras, so a dict of classes would force `import bos.sdk` itself to pull in both 97 MB vendor wheels — the shipped `EXTERNAL_AGENT_KINDS: dict[str, str]` (`harness.py:64-67`) holds `"module:Class"` strings that `_load_external_runtime` (`:72-91`) resolves with `importlib` on first build; and `.pop` would erase `external_runtime` from the very config object that becomes the runtime's own `cfg`, which `boscli inspect` reads back to answer "which vendor backs `george`?" — the shipped dispatch (`:440-453`) uses `.get`. **§3.8** described one `mcp.server.mcpserver.MCPServer` with per-agent filtering in an HTTP middleware; that mechanism cannot work at all, because a middleware sees a request and a response byte-stream, never the MCP-level `tools/list` body it would have to filter, so every agent would have seen every tool. The shipped `BosToolMcpServer` (`mcp_egress.py`) instead builds an `mcp.server.lowlevel.Server` with `on_list_tools`/`on_call_tool` handlers that read the caller's bearer token off `ServerRequestContext.request` — attached per inbound message by `mcp` 2.x's streamable-HTTP session runner (`streamable_http.py`'s `_message_metadata`, read back in `runner.py`'s `_make_context`), not per connection, which is what lets one kept-alive HTTP connection carry many agents' calls correctly. `MCPServer.streamable_http_app` was also the wrong class named for the method actually called — both classes expose a method by that name, but the object served is the lowlevel one — and `MCPServer.add_tool` turns out to have no schema parameter at all (it introspects the wrapped function's signature), which is the concrete reason a `**kwargs` closure over `ep_tool.invoke` could never have worked through it. **§3.9**'s table claimed `max_iterations` maps to Claude Code's `options.max_turns` while having no Codex counterpart; as shipped, `_shared.py`'s `_DROPPED_KEYS` — one set, read for both runtimes — drops it unconditionally, and its own comment calls it a key "with no counterpart in either runtime," contradicting the table's Claude Code column. This is not a considered reversal so much as Layer 2 arriving before Layer 4: the mapping stays the design target, but it will only be true once `ClaudeCodeAgent.__init__` pops `max_iterations` and translates it before handing the rest of its config to `parse_external_config`; a note beside the table row says so.

  The two passages flagged for verification rather than assumed correction held up. §3.4's `george.md` example (`_parent: codex`, a `cwd`, a `permission`, and an `mcp_tools` YAML block) parses exactly as shown — `_parse_simple_yaml_mapping`/`_parse_frontmatter_block` (`workspace.py:229-262,284-300`) support both the scalar and the indented-list form used there — and every other claim in §3.4's prose (the `_EXTERNAL_RUNTIME_SPECS` pseudo-factory table at `workspace.py:77-80`, its merge into `_resolve_agent_inheritance` at `:664`, the `externally_backed` check gating the `[agent.defaults]` skip at `:683`) matches the shipped `Workspace.bootstrap_platform()` line for line.   Beyond the four corrections, the ledger and the code together surface findings the spec did not anticipate. `AgentPort` is a `Protocol` with a `name` **property**, so `issubclass(Agent, AgentPort)` raises `TypeError` — Python refuses `issubclass` on a Protocol with non-method members — and every conformance check in the suite had to become `isinstance` against a real, constructed `Agent` instead. `mcp`'s `ServerRequestContext` is generic over *two* type parameters (`LifespanContextT`, `RequestT`), and `RequestT` defaults to `Any`; annotating the handler context as `ServerRequestContext[Any]` type-checks but leaves `ctx.request` silently `Any`, so pyright verifies nothing about the one authorization-relevant attribute in the file — caught by a deliberate `.headerz` typo probe that zero-errored under `[Any]` and one-errored under `[Any, Request]`, and confirmed independently by a second reviewer reading the vendored type definitions. The reference sketches for `mcp_tools` and `native_options` in the Layer 2 plan both coerced a bare string into per-character list entries wherever `dict()`/iteration met an author's TOML typo; both are now explicit `ValueError`s (`_shared.py`'s two "must be a list"/"must be a table" checks) rather than silent corruption. `read_native_session_id`'s first cut called `get_messages(active_only=True)` — BOS's normal default — which would have made a session's `native_session_id` permanently unrecoverable the day anything wrote a compaction summary over an external chat; it now scans with `active_only=False`, proven by `test_the_session_id_survives_a_summary_written_after_the_turn`. A same-day fix for a blank-vs-whitespace session id introduced a worse bug — `session_id.strip() or None` strips the *returned* id, so a vendor id of `"  thread_abc  "` would come back edited — caught before merge and now covered by `test_a_session_id_with_surrounding_whitespace_is_returned_unchanged`, which is the more interesting result: `.strip()` is used only to test for blankness, never to transform the value handed back to the vendor. And the isolation guard written for §7.27 was itself shown to be weak before it shipped: two of its three assertions passed vacuously under the exact mutation they existed to catch, because clearing both tracked fields unconditionally in `__aexit__` satisfies an equality check regardless of whether a new object was actually built; only a direct `servers[0] is not servers[1]` identity check closes that gap, and it is what ships.
